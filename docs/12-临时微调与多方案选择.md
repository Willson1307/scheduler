# 临时微调 + 多方案选择

> 日期：2026-09-25 ｜ 起因：队长两点意见
> ① 「MVP 只要不和硬规则冲突一律警告，可以设计：给出多种方案，选择」
> ② 「有无临时微调功能？这一场景也很常见」
> 结论：**两条都成立，而且它们互相配套**；临时微调是**当前设计的真实缺口**（第 13 条，V13）。

---

## 第一部分：多方案选择

### 1.1 现状：算得出多个，但只给一个

`m2.py:372` 是 `best = min(results, key=lambda r: r.plans[0].cost)` ——
候选方案**其实已经全部算出来了**，只是取了代价最小的那一个直接应用。
改成返回 top-N **几乎零额外计算成本**。

### 1.2 为什么值得做（四条独立收益）

| 收益 | 说明 |
|---|---|
| **顺带解决 V11** | 只给一个方案时用户无从判断对错；给 3 个 + 差异说明，用户才能验证 → 信任度 |
| **「人在回路」的落地** | 与 `docs/04` 的边界完全一致：**AI 提想法，求解器校验，人来拍板**。多方案是这个叙事最直观的物证 |
| **放大权重学习的价值** | 方案的**排序**由软约束权重决定。权重是否"像本校"，用户看排序一眼就能感觉到 |
| **直接抬满意度** | 教师感觉"系统在帮我决策"而不是"系统在替我决策" |

### 1.3 🔴 与「容量降级为警告」是配套的

容量一旦从硬约束降为警告，**"有没有警告"就成了方案之间可比较的维度**：

- 方案 A：代价最低，但教室容量 ⚠️ 超 8 人
- 方案 B：代价 +2，容量无警告
- 方案 C：改动面最小（只动 1 条日程），但要占用教师第 8 节

**没有多方案，警告就只是个无用的提示**（用户看不到别的选项）；
没有警告，多方案就只有一个"代价"维度可比。**两者必须一起做。**

### 1.4 设计要点（三条硬要求）

1. **每个方案必须带差异说明**，否则用户没法选：
   「改数学课（影响 2 个班）」/「改活动（影响 1 个班、不动课表）」
2. **量化影响面**：改动几条日程、影响多少对象、代价多少——三个数都要有。
3. **必须有区分度**：top-N 里若两个方案的 `日期+节次` 完全相同，只显示一个。
   `_candidate_masks` 生成的候选可能高度相似（都挪到相邻节次），
   **需要加去重规则**，否则"三个方案"看起来像同一个，反而显得系统没本事。
4. N = **3**（MVP）。少于 3 看不出选择，多于 3 决策瘫痪。

### 1.5 成本

约 **0.5 天**：`m2` 返回 top-N（0.5 小时）+ 差异说明生成（2 小时）+ 前端对比卡片（3 小时）。
属 Ryan（`api_resolve.py`）+ 独此一嘉（`web/`）协作，需先定返回结构（进 `docs/07` 契约）。

## 第二部分：临时微调（V13，当前缺口）

### 2.1 先分类：所谓"临时微调"其实是四种不同的事

| 场景 | 例子 | 现状 |
|---|---|---|
| **a. 临时占坑** | 运动会占掉周三下午 | ✅ **已支持**（一次性日程 + 冲突检测） |
| **b. 临时取消** | 王老师周三第 2 节外出教研，**只这一周** | ❌ **不支持** |
| **c. 临时改点** | 本周三第 2 节改到周五第 3 节 | ❌ **不支持** |
| **d. 长期改点** | 从第 10 周起数学课换到下午 | ❌ 不支持（可用再建一条周期 + 改 `valid_from` 变通） |

**缺口是 b 和 c**。周期日程按 `week_parity + slot_bitmap` 展开，
**没有任何机制说"这一周例外"** —— 这是结构性缺口，不是没写 UI。

### 2.2 为什么必须补（比看起来重要）

- **它是教师日常最高频的操作**。我们的卖点是"撞车难调"，但真实日常里最高频的不是"排新课表"，
  而是"这周有个变化"。系统只能排不能改 → 教师用完一次就不用 → **试用数据（25%）难看**。
- 它是**活动之外的第二高频场景**，两者共用同一套时间占用模型（这正是我们归一化的意义所在）。
- 与 V10（撤销）天然配套：微调改错了要能回退。

### 2.3 🔑 关键洞察：它与 A1（调休）是**同一类问题**

| | A1 调休 | V13 临时微调 |
|---|---|---|
| 本质 | 周期规则的**日期级例外** | 周期规则的**日期级例外** |
| 粒度 | 整天（这天按周几上课） | 单条日程 × 单日 |
| 现状 | `calendar_exceptions` 有 `makeup` 未实现 | 完全没有 |

**应当用一张表统一解决**，而不是各做一套（各做一套 = 正是我们一直警惕的"割裂"）。

### 2.4 方案：统一的例外表（一次设计，同时解决 A1 + V13）

```sql
CREATE TABLE IF NOT EXISTS schedule_exceptions (
    id          TEXT PRIMARY KEY,
    org_id      TEXT NOT NULL,
    scope       TEXT NOT NULL CHECK (scope IN ('day', 'schedule')),
    -- day      : 整天级（调休补课 / 停课 / 换作息）→ 对应 A1
    -- schedule : 单条周期日程 × 单日（临时取消 / 临时改点）→ 对应 V13
    target_id   TEXT,              -- scope='schedule' 时是 schedule_id；scope='day' 时为 NULL
    date        TEXT NOT NULL,     -- 生效日期（ISO）
    mode        TEXT NOT NULL,     -- cancel / move / as_of / special
    as_of_dow   INTEGER,           -- mode='as_of'：这天按周几的课表上课（1-7）
    new_mask    TEXT,              -- mode='move'：该日改用这个掩码（十六进制）
    set_id      TEXT,              -- mode='special'：这天用哪套作息
    note        TEXT,
    created_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_sched_exc_lookup
    ON schedule_exceptions(org_id, date, scope);
```

四种 `mode` 覆盖全部场景：

| mode | 用途 | 展开时的行为 |
|---|---|---|
| `cancel` | 临时取消（请假/停课） | 该日这条周期日程**不展开** → 槽位被释放 |
| `move` | 临时改点 | 该日改用 `new_mask` |
| `as_of` | 调休补课（**A1**） | 该日按 `as_of_dow` 的课表展开 |
| `special` | 换作息 / 考试周 | 该日用 `set_id` 这套作息（配合 `docs/10` 的 slot_sets） |

### 2.5 🔴 一个必须写进规格的陷阱

**例外表必须被两处同时读取**：

1. `expand_periodic()` —— 生成占用时应用例外
2. `hard_violations()` —— **排课/消解时也要应用**

只改一处会出最坏的错误：占用显示"第 2 节空着"，但排课时系统其实按"有课"处理（或反之），
**一键消解给出的方案落在真实有课的槽位** → 等于把我们宣称要解决的核心缺陷重新引入。

### 2.6 MVP 范围建议

| 做 | 不做（二期） |
|---|---|
| `cancel`（请假/停课） | 两条课**对调**（= 两次 move，引导用户做两步） |
| `move`（改到指定节次） | `special`（换作息，配合 slot_sets） |
| —— | 批量例外（整周取消） |

**`as_of`（调休）**：你已决定纳入 MVP，与 `cancel`/`move` **同一张表同期实现**，
成本约 1–1.5 天（分做两套要 2 天以上）。

### 2.7 成本与归属

- 约 **1–1.5 天**，动 `occupancy.py` 展开逻辑 → **领域层红线，须走 E2 例外流程 + 队长批准**。
- 建议归属 Ryan（schema.sql 末尾追加是他的独占范围，`occupancy.py` 改动需 E2 批准）。
- 配套：UI 上"某节课 → 右键 → 本周例外"入口（独此一嘉）。
