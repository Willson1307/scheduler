## 第二部分：外脑提示词（可直接复制）

> **使用说明**：发给外部模型时**不要带本文件的迭代过程**（"此前判断过时/用户更正"之类一律删除）。
> 三个视角各发一个模型，**不要把同一模型的两份输出当二源互证**。

### 提示词 A：领域完整性视角（推荐 DeepSeek / Kimi）

```
你是一个校园日程调度系统的架构评审者。请用「特殊场景」反过来检验这个设计有没有漏洞。

【系统是什么】
把「长期重复的课表」和「一次性活动」归一化到同一套时间占用模型，做统一冲突检测与自动消解。

【核心技术事实】
1. 时间占用用位图表示：一周 7 天 × 每天最多 16 节 = 112 位；
   位号 = (周几-1)×16 + (节次-1)。掩码存十六进制文本。
2. 冲突检测 = 位图按位与；结果非 0 即冲突，结果里为 1 的位就是冲突槽位。
3. 课表与活动共享底层，都归一化为「(日期, 当天槽位掩码)」，冲突检测只有一套。
4. 对象是 DAG（有向无环图）+ 闭包表，允许一个对象有多个父（学生可同时属班级和社团）。
5. 对象 ≠ 账号：可存 1500 个学生对象用于调度，但只有真正要登录的人才有账号。
6. 约束分两层：硬约束（撞课，必须排除）与软约束（容量、单日上限、连堂、不排末节，只计代价）。
7. 求解器是自研的回溯搜索；AI 只负责「听懂人话」和「解释结果」，不负责搜索计算。
8. 技术栈：Python 标准库 + SQLite，零第三方依赖，必须断网可跑。

【已知并已确认的边界】
- 非整节（如 14:15-15:00）支持有限
- 跨天活动需拆成两条记录并用同一个 group_id 关联
- 不做实时推送，客户端 10 秒轮询
- 学生不持有终端，只有教师和管理员有账号

【我要你做的】
列举"真实校园里会发生、但上面的设计可能没考虑到"的特殊场景。重点找：
- 会导致系统"报无冲突但实际有冲突"的场景（这类最危险）
- 会导致数据静默丢失或静默改写的场景
- 时间维度上的边界（调休、换季、跨天、跨周、学期边界、节假日叠加单双周）
- 对象关系上的边界（转班、多父、删除、空组、深嵌套）
- 求解器在极端输入下的行为（无解、连锁冲突、超大规模）

【输出格式】每条一行表格：
| 场景 | 预期正确行为 | 如果没处理会怎样 | 严重度（高/中/低） |

只列你有把握的场景，不要凑数。不要编造具体学校的规章制度，涉及不确定的一律标注"需确认"。
最多 15 条，按严重度排序。
```

### 提示词 B：现场演示与赛事风险视角（推荐 千问 / 文心）

```
你是中学生科技创新比赛的评委。请帮我找"现场会翻车"的风险点。

【作品】一个校园日程调度系统：课表与活动统一管理，能自动检测时间冲突并一键给出消解方案。

【现场条件】
- 5 分钟演示 + 5 分钟答辩，展台形式，评委站着看
- 现场**可能没有网络**，必须有断网也能跑的方案
- 评委会核查源代码验证原创性
- 要求有真实用户体验数据：试用人数、平均使用时长、任务完成率、满意度
- 评分权重：工程实现 30%、创意选题 25%、应用与社会价值 25%、展示与答辩 20%
- 技术栈 Python 标准库 + SQLite，零第三方依赖

【我已经想到的风险，不用重复】
演示数据被消解完就没冲突可演示了；登录限流可能锁死现场；断网没演练过；
评委要当场看源码但仓库是私有的；展板和纸质项目书还没排期。

【我要你做的】
列举我**没想到的**现场风险，特别是：
1. 演示过程中最容易出现"卡住/空白/报错"的操作序列
2. 评委最可能追问、而我们答不上来的问题
3. 真实体验数据里哪些数字经不起追问（比如时长虚高、人数重复计算）
4. 答辩时哪些说法会被认为是夸大或虚假宣传

【输出格式】
| 风险 | 触发条件 | 后果 | 现在该怎么准备 |

最多 12 条，按"会不会当场失分"排序。不要泛泛而谈，要具体可执行的准备动作。
```

### 提示词 C：真实用户体验视角（推荐 豆包）

```
你是做用户研究的。我要让中学教师试用一个校园日程调度系统，请帮我找"用户会怎么用坏它"的场景。

【系统能做什么】
- 看到本周课表与活动的周视图，冲突会标红
- 一键消解：系统给出 3 个方案，用户选一个应用
- 临时微调：某节课本周取消或改到别的节次（有撤销）
- 按组授权：查看 / 编辑 / 管理 / 拥有 四档

【用户是谁】
中学教师，约 150 人，试用 15 人，10 天窗口。他们不是技术人员，没人教，第一次打开就自己用。

【我要采集的四类数据】试用人数、平均使用时长、任务完成率、满意度。

【我要你做的】
1. 列举教师第一次使用时最可能卡住或误解的地方（10 条以内）
2. 哪些操作会导致"任务完成率"被算低（比如用户以为没成功其实成功了）
3. 哪些设计会让"平均使用时长"虚高或虚低
4. 满意度问卷该问什么才能拿到真实反馈，而不是礼貌性好评

【输出格式】
| 问题 | 用户会怎么表现 | 对我们的数据/体验的影响 | 建议怎么改 |

最多 12 条。要具体，不要说"加强引导"这种空话。
```

## 第三部分：外脑结果回收后的处理规则

1. **具名证据 > 二源一致 > 单源 > 自评**：
   外脑列出的场景，凡是**能指出具体后果**的优先采纳；只说"可能有风险"的降级处理。
2. **同一模型的两份输出只算一源**，不得互证。
3. 外脑提到的场景若已在本文档第一部分，标注"重复"即可，不新增。
4. 新发现的高危场景追加到 `docs/10` 第五部分，并**同步建卡或更新已有卡**，不要只在文档里记一笔。
