## 1. 🔴 事故一：`--today` 不加，材料与实物不符

### 1.1 现象（两组对照实测，同一个库、同一条 curl，只改启动参数）

| 组 | 启动命令 | `server_date` | `remaining_before` | `remaining_after` |
|---|---|---|---|---|
| **A** | `--today 2026-09-08` | 2026-09-08 | **23** ✅ 与材料一致 | 0 |
| **B** | 不带（当天是 10-03） | 2026-10-03 | **1** 🔴 | 0 |

> ⚠️ **B 组比「报错」更危险**：它**不报错**，`remaining_after` 仍是 `0`，页面上显示「已消解 1 处冲突」。评委看到的是一个**能跑、但数字不对**的系统——这在答辩里比直接崩掉更难解释。

### 1.2 根因（已定位到行）

- `src/server/api_resolve.py:115` 的 `_resolve_window(cfg)`：消解接口的**扫描窗口 = `cfg.today` 所在周（周一~周日）**。这是 `docs/07 §4` 定的「本周」语义，**本身没错**。
- 演示库的学期起点是**固定**的 `2026-09-07`（`scripts/reset_demo.py:34` `TERM_START`），**全部 23 处冲突都密集排在这一周**（第 2/3/4 周各只有 1 处）。
- 不传 `--today` 时 `cfg.today = date.today()`。**10-03 当天 → 窗口 = 09-28~10-04 → 只覆盖 1 处冲突。**
- ⚠️ **这个坑会随日期漂移**：越往后拖，`cfg.today` 离 09-07 越远，窗口越扫不到东西。**现场当天（10-23）不加分句，连 1 处都可能扫不到。**

> 10-03 实测四（扫 `data/demo.db`，非推断）：
> ```
> 第1周 09-07~09-13  <- --today 2026-09-07 / 09-08  -> 23 处
> 第2周 09-14~09-20                                ->  1 处
> 第3周 09-21~09-27                                ->  1 处
> 第4周 09-28~10-04  <- 当天 10-03 所在周->  1 处
> ```
>
> 接口层复现（`POST /api/resolve`，`feat/server-api` 当时）：
> ```
> A 组（--today 2026-09-08）：applied=2  remaining_before=23  remaining_after=0  termination=ok
> B 组（不带 --today）      ：applied=1  remaining_before=1   remaining_after=0  termination=ok
> ```

### 1.3 铁律

**每次启动服务端，命令里必须带 `--today 2026-09-08`。**

- 为什么是 `09-08` 而不是 `09-07`：`monday_of()` 取该日期所在周的周一，`09-07`/`09-08` 同在第 1 周内，效果逐字相同。选 `09-08` 是因为与已实测复现 `23 → 0` 的那次命令完全一致。
- **不许临场想「今天几号」。** 抄 §0 或 §3.1 的命令，别改日期。

## 7. 🔴 事故二：代码不在 main 上，接口直接 404（L2 降级也救不了）

### 7.1 现象与实测证据（10-03）

B4 消解 API 交付后**一直只在 `feat/server-api` 分支上，没合main**：

```
$ git cat-file -e main:src/server/api_resolve.py
fatal: path 'src/server/api_resolve.py' does not exist in 'main'
$ git branch -a --contains 2fe61b0
  feat/server-api
  remotes/origin/feat/server-api← 只有这两个，main 不在其中
```

main 上实测（服务端起得来、`doctor` 也 14/14 全绿，但接口是死的）：

```
GET/POST /api/resolve  →  HTTP 404  {"error": "接口不存在：GET /api/resolve"}
```

**为什么这条特别危险**：

| 事实 | 后果 |
|---|---|
| `doctor.py` 14/14 全绿 | ✅ **体检完全测不出这个问题**（doctor 不检查业务路由） |
| `demo_cli.py` 能跑出 23 → 0 | ✅ **L2 降级也测不出**（它不经过 HTTP） |
| 页面能打开、周视图能渲染 | ✅ 看起来「系统正常」 |
| 前端点「一键消解」 | 🔴 **直接 404，白屏或弹「接口不存在」** |

也就是说：**所有现成的检查手段都会说「OK」，只有真实打一次接口才会暴露**。这是它比 §1 更难发现的原因。

### 7.2 处置

**10-03 已合 main**（merge commit `319535f`，571 行纯新增0 删除），合并后 main 上复测：

```
main 上 GET/POST /api/resolve       →  HTTP 200 ✅（不再是 404）
main 上 POST /api/resolve           →  remaining_before=23  applied=2  remaining_after=0  termination=ok
main 上 unittest discover -s tests  →  Ran 42 tests  OK (skipped=1)
main 上 doctor                      →  14/14 全部通过 ✅
边界：mode=bogus       → 400  「mode 必须是 minimal/balanced/optimal」
边界：group=NOSUCH→ 404  「组不存在」
边界：plan_index=-5     → 400  「plan_index 必须是非负整数」
限频：匿名桶第 11 次   → 429  「请求过于频繁，请稍后再试」
```

**但合并只是当时的快照，现场前仍要自己验一遍**（§2 第 10 条）：

```bash
# 🔴 2026-10-06 订正：B3 鉴权（a21588b）与 B4 越权修复之后，
#    /api/resolve 与 /api/conflicts **无 token 一律 401**。
#    现场照抄旧命令（不带 token）会拿到 401，被误判为「接口坏了」——
#    而 §7.1 记录过一次真的「接口不存在」事故，两者混淆会浪费宝贵的现场时间。
#    **必须先 login 拿 token。**

# 第 1 步：登录拿 token
TOKEN=$(curl -s -X POST "http://127.0.0.1:8000/api/login" \
      -H "Content-Type: application/json" \
      -d '{"login":"admin","password":"admin123"}' \
     | python -c "import sys,json;print(json.load(sys.stdin)['token'])")

# 第 2 步：带 token 调消解
curl -s -X POST "http://127.0.0.1:8000/api/resolve" \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer $TOKEN" \
     -d '{"org":"试用学校","mode":"m2"}'
# 必须看到：remaining_before = 23   ← 这是材料里的数字

# 若看到 401 → token 没拿到或已过期，重新走第 1 步
# 若看到 "接口不存在" → §7.1 复发，先确认 git branch --show-current
```

> ⚠️ **限频说明**：`RATE_LIMIT = 10次/分钟/桶`，**现在按 token 计数**（不再是匿名共用桶）。
> **演示前测试时用过的桶，现场可能还在限频窗口内** → 现场若偶发 429，等 60 秒再点即可，不是 bug。

### 7.3 现场纪律

- **现场只从 `main` 拉代码**，不从任何 feature 分支拉。
- 若现场 `git pull` 后行为异常，**先 `git branch --show-current`**，再打一次 §7.2 的 curl——这两步能在 10 秒内定位是「分支错了」还是「接口坏了」。
