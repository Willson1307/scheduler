# 架构速览（给队员看的一页纸）

## 一句话概括

> 一切时间占用都归一化为「(日期, 当天槽位掩码)」，冲突检测只有一条规则：
> **同一对象同一天，两条日程的掩码按位与 ≠ 0 → 冲突**。

---

## 1. 三层数据模型

```
organizations  组织（学校）—— 不进对象图
      │
      ▼  建组织时自动创建"全校"根组
objects        对象：group（班/年级/社团） / user（教师/学生） / resource（教室）
      │
      ▼  多父 DAG + 闭包表
object_edges   (祖先, 后代, 距离)，含自反边。一个学生可同时属班级+社团
      │
      ▼  身份层（与对象层正交）
users          只有真正要登录的对象才有这一行
```

**为什么对象图用 DAG 而不是树？**
一个学生可以同时属于「高一(3)班」和「机器人社团」。单亲树表达不了，
强行表达就要复制行或写特判，后面权限判定和冲突检测全要跟着打补丁。

**为什么配闭包表？**
"某年级下所有学生"这类查询非常频繁。闭包表把它变成一次索引扫描，
代价是空间（约 1–2 万行）与建边时的一次增量维护。

---

## 2. 槽位与位图

```
period_slots  org_id / 周几 / 第几节 / 起止时刻 / enabled
```

- 槽位**不是写死在代码里的**，改这张表就能改作息；
- 位号 = (周几 − 1) × 16 + (节次 − 1)，**位序固定**，配置怎么改都不影响已有掩码；
- 掩码存**十六进制文本**（112 位，SQLite 整数放不下）；
- 单双周用 `week_parity` ∈ {0 每周, 1 单周, 2 双周}；"第几周"不入库，从 `terms.start_date` 推算。

---

## 3. 统一底层（本项目最关键的设计）

```
周期日程：week_parity + slot_bitmap + 生效区间  ─┐
一次性活动：start_at / end_at 时刻             ─┴→  展开 → {日期: 当天掩码}
```

展开之后两者完全同构，于是：

- 冲突检测只写**一套**位运算；
- **AI 排课看得见已安排的活动**——如果两套东西各存各的，排课就会把课排在活动上，
  这是真实的功能缺陷，不是理论问题；
- 顺带白拿的能力：统一冲突报告、真实负载（课表 ∪ 活动）、活动选址建议、单一时间轴视图。

**表结构用类表继承**：`schedules`（共用字段）+ `schedule_periodic` / `schedule_once`（特有字段），
应用层通过 `v_schedule_full` 视图查询，不必手写 JOIN。
故意不用"两张独立表"——两张表会天然诱导写出两套逻辑，而两套逻辑正是割裂的根源。

---

## 4. AI 排布：求解器负责算，大模型只负责听懂人话

三种模式共用同一套占用矩阵 + 硬约束引擎 + 软约束代价函数，只是搜索策略不同：

| 模式 | 场景 | 策略 | 时限 |
|---|---|---|---|
| M1 | 新学期全局排课 | 全局 CSP 回溯 + 前向检查 + MRV，超时转局部搜索 | ≤60s |
| M2 | 冲突消解（微调） | 最小改动搜索 | ≤2s |
| M3 | 局部补排（单班/单教师） | 小规模 CSP | ≤5s |

**为什么不让大模型直接排课**（答辩大概率被问）：

1. 大模型做的是文本续写，不是约束搜索——600 个排课单元 × 50 槽 × 20 教室的空间下必然排出冲突，而且它自己查不出来；
2. 求解器能给出"所有硬约束均满足"的保证，大模型不能；
3. 不可复现，现场会翻车；
4. 会被问到"你的 AI 是训练的还是调接口"——用求解器 + 从本校课表学权重，两个都能正面回答。

---

## 5. 偏好权重学习

从本校**公开**的往期课表统计历史满足率 p，权重 w = −ln(1 − p)：

- 学什么：主科是否偏好上午、教师日均课时、同科单日上限、连堂习惯；
- 学出来的权重喂给求解器的软约束代价函数；
- 合规：课表是校内公开信息，但**不得外传、不得关联学籍字段**，项目书里要写明。

---

## 6. 边界与不做的事

- 学生 MVP **不开登录账号**（学生无手机/平板/一体机，发密码没有合法路径）；
- 活动**没有报名流程**，由有权限者直接指定参与者对象；
- 全程**本地 SQLite，断网可跑**，不依赖任何外部 API。
