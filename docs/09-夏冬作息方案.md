# 夏冬两季作息：解决方案（待队长拍板）

> 状态：**方案待选**，尚未实现。2026-09-25 提出。
> 提出原因：本校有夏季 / 冬季两套作息，而当前 `period_slots` 只有一套时刻。

---

## 一、先确定一件事：影响面其实很小

位号公式：

```
位号 = (周几 − 1) × 16 + (节次 − 1)
```

它**只依赖"周几 + 第几节"，不依赖几点上课**。所以：

| 数据 | 换季是否受影响 | 原因 |
|---|---|---|
| 周期课表（`slot_bitmap`） | ✅ **完全不受影响** | 存的是位串，与时刻无关 |
| 冲突检测（按位与） | ✅ **完全不受影响** | 只做位运算 |
| 一次性活动（`start_at/end_at`） | ⚠️ **受影响** | 时刻 → 格子的映射依赖当前槽位配置 |
| 前端周视图显示的时刻 | ⚠️ 受影响 | 显示的是 `start_time/end_time` |

**结论**：换季不是架构问题，是"时刻 ↔ 格子"这一层需要季节感知。

---

## 二、一个必须知道的风险

`occupancy.py` 的 `build_occupancy()` 调用 `expand_once(start_at, end_at, cfg)`，
即**一次性活动是每次查询时用当前 SlotConfig 实时展开**，不是入库时固化。

后果：换季改表后，历史活动会被**重新解释**。

```
例：9 月（夏季作息）排了一个 14:00–15:00 的活动 → 展开为第 6 节
    冬季作息下 14:00–15:00 可能对应第 5 节
    → 换季重查，同一活动变成第 5 节，冲突关系可能改变
```

⚠️ 最坏情况是**原本冲突的变成不冲突（漏检）**——这正是本项目要防的事。

> 📌 风险大小取决于一个待确认事实：夏冬作息的**节次编号是否一一对应**（只是时刻平移），
> 还是**节次数量/编号也不同**。若只是时刻平移半小时，影响很小；若编号错位，影响大。
> **→ 待队长向校方核实（to-confirm）。**

---

## 三、三个方案

### 方案 C（MVP 先用）：单套作息 + 换季手工切换

- 当前 `period_slots` 只存**当前季节**的作息。
- 换季时由管理员跑一次更新脚本，改写 `start_time / end_time`。
- **成本：零改动**，不碰领域层，不影响 10/7 死线。

**代价**：上面那个重新解释的风险原样存在。
**缓解办法**：换季时给"跨越换季日的一次性活动"做一次人工复核（或导出掩码快照）。

**适用**：10/7 前的主线阶段。**建议 MVP 用它**。

---

### 方案 A（主线闭环后升级）：加季节维度

- 新增一张季节表（末尾追加，**不动现有 `period_slots`**）：

```sql
CREATE TABLE period_slot_sets (
    id          TEXT PRIMARY KEY,
    org_id      TEXT NOT NULL,
    name        TEXT NOT NULL,          -- '夏季' / '冬季'
    from_mmdd   TEXT NOT NULL,          -- '05-01'
    to_mmdd     TEXT NOT NULL,          -- '09-30'
    priority    INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE period_slot_times (
    set_id      TEXT NOT NULL REFERENCES period_slot_sets(id),
    day_of_week INTEGER NOT NULL,
    idx         INTEGER NOT NULL,
    start_time  TEXT NOT NULL,
    end_time    TEXT NOT NULL,
    enabled     INTEGER NOT NULL DEFAULT 1,
    PRIMARY KEY (set_id, day_of_week, idx)
);
```

- `period_slots` 保留为**默认兜底**（当日期不匹配任何季节时用它）。
- `load_slot_config(conn, org_id, on_date=...)` 增加日期参数，按日期选 set。

**成本**：新增两张表（纯追加，不动现有表结构）+ **改 `slots.py` 的加载逻辑**。
`slots.py` 属领域层现有文件 → 🔴 **须走 E2 流程 + 队长批准 + 31 项老测试全绿**。

**收益**：历史活动可按当时所属季节正确展开，彻底消除重新解释的风险。

---

### 方案 B：给 `period_slots` 直接加 `season` 列

- 最直观，但 SQLite **不支持 ALTER 改 UNIQUE 约束**，
  `UNIQUE(org_id, day_of_week, idx)` 要改成 `UNIQUE(org_id, season, day_of_week, idx)` 必须**重建表**。
- 超出"schema.sql 末尾追加"的允许范围，风险明显高于 A。
- ❌ **不推荐**。

---

## 四、推荐路径

| 阶段 | 做法 |
|---|---|
| **现在 → 10/7** | **方案 C**（零改动）。把"换季需人工复核跨季活动"写进已知限制 |
| **主线闭环后（有余力）** | 升级到**方案 A**，走 E2 审批 |

这样既不拖累 10/7 死线，又留下了干净的上升级路径。
