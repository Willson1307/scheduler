```
本项目为参加嘉祥锦江中学少年科学院第一届"脑洞上线"AI创意设计挑战赛的参赛作品开发。

【目标】用MVP思路开发一个以AI实质解决真实校园/生活问题的网页作品：核心功能少而精、现场演示绝对稳定、AI内核清晰可讲解。评审权重：工程实现30%、创意选题25%、应用与社会价值25%、展示与答辩20%。

【选题与当前状态】
- 项目名：课表活动撞车难调，AI求解一键消解；仓库名：scheduler（不叫 school-scheduler，模型不绑定学校场景，便于后续拓展）。
- 一句话：把课表（长期重复事务）与活动（一次性事务）归一到同一套时间占用模型上，用自建的 AI 约束求解器做统一冲突检测、自动排布与最小改动消解。
- 已完成：B0 数据层（对象图 DAG+闭包表、节次与位图、统一占用与冲突检测）、B4 AI 内核（硬/软约束引擎 + M2 冲突消解，一键消解实测 23 处冲突→0）。31 项单元测试全绿，零第三方依赖，断网可跑。
- 在建（2026-09-25 状态，目标 10/7 可试用）：按组的四档权限系统、Web 服务端、前端（周视图/冲突列表/一键消解）、自然语言入口、使用埋点。人员分工见下【团队与分工】。
- ⚠️ 对外表述铁律：只把"已实现"说成"已完成"。在建功能只能写进"技术方案/在建进度"，评委会核查源代码，夸大表述会被当场揭穿。每完成一个检查点，再把对应条目从"在建"移到"已完成"。
- 技术栈：Python 标准库（http.server）+ SQLite，不引入 Web 框架，保证现场断网可跑；领域层全部写成与框架无关的纯函数，将来要换 FastAPI 只需替换一层薄适配。零第三方依赖已写进 requirements.txt。
- 五条硬性设计约定（改动前先确认）：
  1. 对象 ≠ 账号：objects 可全量存 1500 名学生（调度与冲突检测用），users 只放真正要登录的人；
  2. 位图是加速层不是真相层：真相是 period_slots 配置 + 周期规则 + 起止时刻；
  3. 课表与活动共享底层：都归一化为「(日期, 当天槽位掩码)」，冲突检测只有一套位运算，排课因此看得见已安排的活动；
  4. 求解器负责"算"，大模型负责"听懂"和"解释"：求解过程分三步（理解需求 / 搜索计算 / 解释与微调），只有第②步严禁交给大模型。大模型可以提调整建议，但每一条都必须回送硬约束与冲突检测校验，不通过即驳回——一句话，让 AI 提想法，让求解器做裁判；
  5. 权限按组、四档、沿组织树继承：查看 / 编辑 / 管理 / 拥有，沿对象图祖先链继承，多条路径取最高档，全局角色当天花板；列名用 level（GRANT 是 SQL 保留字）；刻意不做"负权限 deny"（多父 DAG 下语义不自洽）。

【当前阶段约束】先搭基础框架，不往深处动工
- 原则：先打通一条能从头跑到尾的细线（启动 → 打开页面 → 看到冲突 → 一键消解），每一层先做到"能通"，深度留到闭环跑通之后再补。
- 暂缓（主线闭环跑通前不要碰）：M1 全局排课、M3 局部补排、偏好权重学习、拖拽排课、CSV 批量导入 1500 人、给学生开账号。
  ⚠️ 口径更新：其中 M1、偏好权重学习、prompt 入口已从"砍掉"改为"可选恢复"（工期重估后编码不再是瓶颈），但排在最后一批，**主线不闭环就不动**。学生账号不在此列——那是学校场景限制（学生不持有终端），不是工期问题。
- 深浅边界见仓库内 docs/02-基础框架边界.md，新增功能前先对照该文件判断属于哪一层。
- 动手前必读两个文件：AGENTS.md（技术栈红线、领域层只读范围、三人文件所有权、提交规范）｜docs/07-API契约.md（前后端并行开发的唯一依据）。
- 分批推进的防错三原则：①规格逐批冻结，不等全部定稿才开工；②每批留一个可运行检查点 + 自动化测试，防止错误累积；③每批产出看得见的东西（一个页面、一个能跑的接口），别只在中间层打转。
```
