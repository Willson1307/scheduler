## 0.5 🔴🔴 一师一组织：多位老师怎么各自消解（2026-10-11 新增，必读）

### 问题

队长提问：**「试用的一个老师把冲突全消了，剩下的老师怎么办？」**

一键消解是**真改库**，不是预览。共享单组织时：
第一位老师点完 → 全组织 32 处冲突归零 → 后面 11 位老师进来看到的是 **0 冲突**。
后果有两层：
- 老师以为系统坏了，或者根本不会去点消解 → **采不到完成率**（有分母 `task_start`、没分子 `task_success`）
- 章程第八条(六)要的真实体验数据直接残废

### 方案选型

| 方案 | 结论 | 理由 |
|---|---|---|
| A 每人一个库文件 `trial_t01.db`… | ❌ 否决 | 启动命令要带参数、12 份库各跑一遍脱敏检查、报告要写合并逻辑、老师拿错文件登不进自己那份 |
| B 每次试用前跑一次 build 重置 | ❌ 否决 | 现场手抖就忘；老师之间无法同时用；等于把数据管理甩给主持人 |
| C 把冲突从 32 加到 384 | ❌ 否决 | 只是把问题推后 N 位，第 N+1 位老师照样归零 |
| **D 一师一组织** | ✅ **采用** | 零新增运行时逻辑，见下 |

### D 为什么成立（已核代码 + 实测）

系统**本来就按 `org_id` 硬隔离**：

- `scan(conn, org_id, ...)` —— 只扫本组织
- `/api/conflicts`、`/api/schedules`、`/api/objects` —— 都经 `K.resolve_authorized_org()`，
  它只认「当前用户有授权的组」，跨组织直接 403
- `/api/resolve` —— 同上，且可动集合按本组闭包算

所以给每位老师一个独立组织，消解**天然互不影响**，不需要写任何新逻辑。
顺带还能当答辩素材：这就是真实的「组织级数据隔离」能力，不是为演示临时搭的。

### 怎么生成

```bash
python scripts/build_trial_org.py --per-teacher
```

产出 **12 个教师组织 + 1 个独立管理员组织**：

| 短码 | 登录名 | 组织名 | 规模 | 第 1 周冲突 |
|---|---|---|---|---|
| T01 | `trial_t01` | 试用学校T01 | 2 班 / 24 人 | 5 组 / 30 处 |
| … | … | … | … | … |
| T12 | `trial_t12` | 试用学校T12 | 2 班 / 24 人 | 5 组 / 30 处 |

- 口令**各自独立**（2026-10-23 起已随机化）：见各自的登录卡（`_登录卡-2026-10-24/`，
  在仓库外，一人一份），**本手册不写口令**
- 登录名**必须带 `trial_` 前缀**：后端据此推短码 `T01…T12` 并判`org_kind='trial'`
- **每组织刻意做小**（2 班 24 人）：老师要能一眼看完所有冲突才愿意点消解；
  数据做大了反而没人用。知情接受的代价是「规模比真实小」，这是特性不是缺陷
- 管理员 `trial_admin` 放在**独立第 13 个组织**——CP-H-S2 修复（2026-10-19，
  甲-2）后 admin 默认只看自己所属组织；trial_admin 要看 12 个教师组织靠
  `build_trial_org.py` 显式授的 12 条根组 `own`（沿祖先链继承到各组织全部组），
  不再走 admin 全库短路

### 验证隔离真的生效（必跑，不能靠推理）

```bash
python scripts/run_server.py --port 8000 --today 2026-10-12 --db data/trial.db  # 另开终端
python scripts/check_trial_isolation.py
```

**期望输出**：

```
T01 消解 HTTP200  {applied:4, remaining_before:30, remaining_after:0, ...}
  trial_t01: count=0 raw_count=0            ← 自己消干净了
  trial_t02: count=5 raw_count=30（与初始一致）  ← 不受影响
  trial_t03: count=5 raw_count=30（与初始一致）
  trial_t12: count=5 raw_count=30（与初始一致）
  T01 token 访问 T02 的组→ HTTP 403（正确拦截）
✅ 组织隔离全部通过
```

> 🔴 **断言必须同时比 `count` 和 `raw_count`**：`count` 是聚合组数（界面口径），
> `raw_count` 是原始条数（消解口径）。只比 `count` 会得出「隔离失效」的错误结论——
> 这个坑本轮首跑就踩了一次。

### 现场注意

- **所有老师同时用这一个 `data/trial.db`**，但各看各的组织，互不干扰
- 老师之间**看不到彼此的班级和课表**（这是设计，不是缺陷）
- 试用结束后（**四类数据导出之后**）再重置：`python scripts/build_trial_org.py --per-teacher`。
  🔴 重置会清空 `event_log` 等真实试用数据（章程第八条六资格项），**导出前严禁重建**
- `trial_t04`/`t07` 登录时若提示失败，先看 §1 的三个参数，**别让老师反复试**
  （2026-10-25 起限流口径：`(login, 来源IP)` **组合锁 —— 连错 5 次锁 60 秒**，
  别人的 IP 登录同一账号不受影响；**不是旧的「账号锁 15 分钟」**，详见 §5.5）

## 0.6 🔴 老师怎么连上（2026-10-11 新增，之前缺这一节）

> **为什么补**：`--host` 默认 `127.0.0.1` **只听本机**，别人连不上。
> 手册原先只写了账号密码，**没写连接方式** → 现场必然卡在这里。

### 先选一条路径（按人数和场地）

| 路径 | 适用 | 老师要做什么 | 门槛 |
|---|---|---|---|
| **A 局域网** | 试用在同一间教室/办公室 | 浏览器开 `http://<你的内网IP>:8000` | 最低，只要能插网线 |
| **B 远程桌面** | 1–3 位熟人老师，异地 | 装向日葵/ToDesk，装你给的「设备码+密码」 | 低，**不用注册、不用记网址** |
| **C 云服务器** | 多人、异地 | 浏览器开 `http://<公网IP>:8000` | 中，需放行端口 |

> ⚠️ **多人同时用远程桌面会互相看见对方操作和课表** —— 那是共享一个桌面。
> 5 人以上同时用请走A 或 C。

### 起服务：云服务器/局域网必须加 `--host 0.0.0.0`

```bash
# 本机自用（默认 127.0.0.1 即可）
python scripts/run_server.py --port 8000 --today 2026-10-12 --db data/trial.db

# 🔴 别人要连 —— 必须加 --host 0.0.0.0
python scripts/run_server.py --host 0.0.0.0 --port 8000 --today 2026-10-12 --db data/trial.db
```

**起对了的标志**：`READY host=0.0.0.0 ...`（不是 `127.0.0.1`）。

###🔴 三条纪律

1. **不要发 `trial_admin`** —— 那是队长用的，能看到全部组织（2026-10-19 起由

## 3. 现场流程（每人一循环）

## 5. 🔴 现场话术（被问到时照说）

> 「系统内置埋点：教师用一次性编号登录，系统记录任务发起、成功、放弃三类事件，
> 按编号去重统计人数、按 5 分钟断线规则剔除挂机时长；试用结束后另收纸质问卷。
> 数据只出聚合数，编号与姓名的对应关系保存在纸质记录里，从不进入系统。」

**若评委问「为什么试用比原计划晚」**（试用启动一再顺延）：

> 「前端埋点与采集链路没验证完就试用，采集不到数据反而是自欺。顺延之后，

## 5.5 🔴 故障对照表（老师报「不行」时先查这张表）

> 2026-11-10 按部署机**实测**口径写，不按旧文档。
> 用法：老师说什么现象 → 查左列 → 按「怎么办」做。⛔ 不要让老师自己猜。

### A. 登录相关

| 现象 | 真实原因 | 怎么办 |
|---|---|---|
| 输口令后提示「登录名或密码错误」 | 口令错（注意**大小写**；复制时**别带首尾空格**） | 让老师重新复制口令，别手打 |
| 同上，但口令确认没错 | 口令表与服务器不同步 | 队长跑 `deploy/reset_trial_passwords.py` 重发口令 |
| 提示「连续失败过多，请 1 分钟后再试」 | 该账号 + 该来源连续输错口令（阈值属内部实现，**不对老师讲**） | **等满 1 分钟**再试。⛔ 不要反复点，越点越锁 |
| 提示「请求过于频繁，请稍后再试」 | 同一来源短时间内登录请求过多（多人同网络 / 反复刷新会触发；阈值属内部实现，**不对老师讲**） | 等 1 分钟；多人同时试用时错开登录 |
| 页面打不开 / 一直转圈 | 服务器实例没在跑，或 8000 端口不可达 | 队长检查实例状态；见 §7.5 关停/重开步骤 |

⚠️ **对外口径统一为「有软限制，稍等再试」，⛔ 不要说出具体次数与时长**——
次数/时长是内部实现细节，说了老师会去试边界。

### B. 看不到东西

| 现象 | 真实原因 | 怎么办 |
|---|---|---|
| 登录成功但**组下拉框是空的** | 该账号没有授权行（`group_roles` 缺） | 队长查：`SELECT COUNT(*) FROM group_roles;` 为 0 就是这个问题，跑 `build_trial_org.py` 重建 |
| 组能选，但**周视图全空** | 选错了组；或该组本周确实没有排课 | 逐个组切换确认；`trial_t01` 正常应有 2 个组可选 |
| 周视图有课，但**冲突列表 0 条** | ① 本周确实无冲突 ② 活动窗口已过期（活动在上一周） | 看周视图是否为空；确认当前是**试用周**（11/09–11/15） |
| 换了个老师的账号，**看到的还是自己的班** | 正常——**一师一组织**，每人只看自己的班 | 不需要处理。别让老师误以为是 bug |

### C. 一键消解相关

| 现象 | 真实原因 | 怎么办 |
|---|---|---|
| 点了「一键消解」**像没反应** | 结果写在下方「消解结果」区（会自动展开）；该组本周本来没有冲突时按钮是禁用的 | 看「已消解 N → M 处」那行；M 不为 0 说明还有硬冲突没解开，去冲突列表看是哪几处 |
| 消解后提示**要审批 / 无权限** | 教师有效档是 `propose`（可提议、不可直接改永久数据） | **这是设计，不是故障**。照 §0.5 走「提议 → 管理员批准」流程 |
| 消解后**冲突数没降** | 该冲突含硬约束（同一人同一时刻、同一教室），无解 | 属正常：算法会留「消不了」的项。看返回里的 `termination` 说明 |
| 点消解后**页面卡住** | 浏览器缓存了旧版 `app.js` | `Ctrl + F5` 强刷；版本号以页面底部「关于」里显示的为准 |

### D. 页面显示

| 现象 | 真实原因 | 怎么办 |
|---|---|---|
| 样式错乱 / 按钮点不动 | 旧缓存（改了 JS 但浏览器用旧版） | `Ctrl + F5`；仍不行则清缓存重开 |

| 字号小 | 现场投影才需要 1 米可读；试用用电脑正常 | 无需处理 |

## 5.7 常见操作怎么做（老师说「我想…」照这节教）

- **看某个班这周怎么排**：先在「当前组」选组，再在「查看对象」选班级，周视图就是它这周的课表。
- **看某天有哪几节被占**：看周视图下方的「每日占用」，例如「第 2 节 周一」。
- **临时取消一节课**（只影响这一天）：点格子右上角的「⋯」，或直接双击格子 → 选「取消今天这节课」。
- **把某节课换到当天别的节次**：同样打开「⋯」→ 选「改到第 N 节」→ 选好节次后点「改到」。
- **改错了想恢复**：在同一个面板点「撤销」，这一天回到原样。
- **找某天下午连续两节都空的时段**：用「查空位」，选对象和连续节数后点查询。
- **要改整周的固定课表**：走「变更请求」，提交后由管理员批准；**批准前课表不会变**。
- **看不到某节课**：先确认「当前组」和「查看对象」选对了，再点「重新加载」。

## 5.8 界面上的数字和颜色

- **「本周 N 处冲突（M 组）」**：N 是原始条数（一处冲突牵涉 3 个班就算 3 条），M 是合并后的组数（同一处只算 1 组）。所以 N 一定大于等于 M，两个数不是重复。
- **红色格子**：这节有冲突，鼠标移上去能看是谁和谁撞了。
- **「已消解 N → M 处」**：消解前 N 处，消解后剩 M 处。M 不为 0 说明还有硬冲突解不开（例如同一位老师被两处同时占用）。
- **按钮是灰的**：当前没有可执行的事。例如本周 0 处冲突时「一键消解」不能点。
- **「每日占用」里的「第 3、4 节」**：这天的第 3、4 节被占用；鼠标停上去能看到原始掩码（技术核对用，老师不用管）。

## 5.9 已知限制（老师问到就照实说，不要含糊）

- **切组后冲突数不变**：冲突按学校整体扫描，切组只决定「你能不能看」（越权会被拒绝）。按组收窄清单还没做，下一步再做。
- **只显示周一到周五**：当前作息配置就是这样，周六周日不排。
- **手机能登录，但体验一般**：建议用电脑浏览器，页面按 768px 以上设计。
- **公告只在本系统内可见**：试用入口页（另一个网址）不会跟着变。

### 7.5 🔴 公网实例关停 / 重开操作步骤（2026-10-24 定稿）

> 现状：试用服务跑在腾讯云轻量 `106.53.214.131`，**8000 端口对 `0.0.0.0/0` 与 `::/0` 全开**。
> **是否收窄放行范围是队长的决策**，本手册只记录怎么操作、怎么验证。

**关停（试用结束当日）**：

1. 登录腾讯云轻量服务器控制台 → 防火墙规则 → 删除（或禁用）**TCP 8000** 的入站规则
   （现行有 `0.0.0.0/0` 与 `::/0` 两条来源）。
2. 只动防火墙规则，**服务本身保持运行**（systemd user 单元 `scheduler-trial` 不动）——
   服务器本地仍可访问，便于队长随时核查/导出数据。
3. 验证已关停（两条都要做）：
   - **手机关 WiFi 用流量**开 `http://106.53.214.131:8000` → 应**超时/无法访问**；
   - 服务器侧 `ssh -i ~/.ssh/wb_deploy ubuntu@106.53.214.131
     "curl -s http://127.0.0.1:8000/api/health"` → 仍应 200（证明只是入口关了，服务没坏）。

**重开（队长决定后）**：

1. 控制台防火墙重新添加 **TCP 8000** 入站规则（来源按队长决策：
   全开 `0.0.0.0/0` + `::/0`，或收窄到试用老师所在网络的出口 IP）。
2. 确认服务在跑：`ssh -i ~/.ssh/wb_deploy ubuntu@106.53.214.131
   "systemctl --user is-active scheduler-trial"` → 期望 `active`；
   若非 active 先 `systemctl --user start scheduler-trial`。
3. 验证已重开：**手机流量**开 `http://106.53.214.131:8000/api/health` → 200。
   🔴 第 3 步只能真机测——控制台显示「已放行」不代表外网真能通（NAT/运营商策略）。
