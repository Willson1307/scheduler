## 2. 🔴 P0 致命缺陷

### P0-1 `rebuild_closure` 清空整张闭包表 —— 一次调用，全校层级关系归零

**🔬 实测输出**：
```
add_edge 之后：root->年级组 depth=1｜root->班级 depth=2｜root->张三 depth=3
rebuild_closure 前后 depth>0 的闭包行数: 6 -> 0     🔴
rebuild_closure 之后 root->年级组 = None（行不存在）
```

**根因**（`object_graph.py:184-191`）——两步的顺序写反了：
```python
conn.execute("DELETE FROM object_edges WHERE depth > 0")          # ① 先删掉所有非自反边
conn.execute("INSERT OR IGNORE ... SELECT id, id, 0 FROM objects") # （自反边已存在，无操作）
direct = conn.execute(
    "SELECT ancestor_id, descendant_id FROM object_edges WHERE depth = 1"  # ② 再去找"直接边"
).fetchall()                                                      # ← 已经被 ① 删光了！
```
`direct` 恒为空 → `adj` 为空 → BFS 什么都不产生 → 闭包只剩自反边。

**触发路径（低频但正常）**：
```
remove_edge(社团, 某学生)   ← 把学生从社团移除，一次普通操作
   → rebuild_closure()
       → 全校 1500 人的所有层级关系被清空
```

**为什么这是最危险的一条**——它**不报错、不抛异常、不写日志**：
- `descendants(班级)` 返回 `[]`
- `build_occupancy` 的组展开循环空转 → **组不再占用成员时间**
- 冲突检测从"能发现班级撞课"退化成"只看个人" → **大面积漏报**
- 用户看到的画面是：**"系统说没冲突"**，而实际上冲突全在

> **现场风险**：答辩演示中若有一次"调整组织架构/移除成员"操作，之后所有冲突数字都会静默失真。
> **修法（约 5 行）**：把 ① 改成只 `DELETE WHERE depth > 1`，或**先 SELECT 出直接边再 DELETE**。
> **必须补的**：一条回归断言「`remove_edge` 之后，其余边的闭包行数不变」。

### P0-2 调休（`makeup`）完全未实现 —— 队长点名要的功能是空的

**🔬 实测输出**：
```
calendar_exceptions = {'2026-09-26': 'makeup'}   ← 已写入"周六调休按周一课表"
该周周期课表展开结果: {2026-09-21: 1}            ← 只有周一
>> 周六(调休日)是否有课: ❌ 无
```

**根因**（`occupancy.py:126`）：
```python
if vf <= d <= vt and exceptions.get(d.isoformat()) != "holiday":
```
只判断了 `!= "holiday"`，**`makeup` 分支根本不存在**。而 `schema.sql:119` 明明定义了
`kind TEXT NOT NULL CHECK (kind IN ('holiday', 'makeup'))` —— **字段留了，逻辑没写**。

调休日在周六，`d.isoweekday()=6` → 查 `period_slots(day_of_week=6)` → 没配周六槽位 →
掩码 0 → **这一天的课表凭空消失**。

> **与队长决策的冲突**：队长 2026-09-25 明确「**调休这个要做，因为不做效果很差**」，
> 且已批准进 MVP。代码里没有。这不是设计问题，是**实现缺口**。
> **修法**：这正是 docs/14 的 `calendar_days.teach_dow` 要解决的——调休日本质是
> "这一天的周几映射被改写"。在 `calendar_days` 落地前，最小修法是：
> `expand_periodic` 遇到 `makeup` 时，用配置的"按周几上"去查槽位，而不是 `isoweekday()`。

### P0-3 「静默跳过」是系统性模式 —— 5 处同源，共同后果是少报冲突

这不是 5 个独立 bug，是**同一个坏习惯的 5 次发作**：
*"算不出来/查不到的时候，`continue` 掉，不告诉任何人。"*

| # | 位置 | 触发条件 | 后果 |
|---|---|---|---|
| 1 | `occupancy.py:155` | 活动时段不落在任何 `period_slot`（午休开会） | 🔬 实测 `expand_once → {}`：**活动完全不存在** |
| 2 | `occupancy.py:127` | 日期不在任何 `term` 区间内 | 🔬 实测 `expand_periodic → {}`：**课表凭空不见** |
| 3 | `occupancy.py:126` | 调休日 `makeup` | 见 P0-2 |
| 4 | `schema.sql:179-190` | `schedules` 有行但扩展表缺行 | `v_schedule_full` 用 **INNER JOIN** → 孤儿行**静默消失** |
| 5 | `slots.py:150-156` | `mask_for_range` 返回 `mask=0, aligned=False` | 调用方把 `aligned` 命名成 `_aligned` **完全丢弃** |

**共同危害**：本系统的全部价值主张是"**AI 求解器保证不漏冲突**"。
而"静默跳过"造出的全是**假阴性**——系统说没冲突，实际有。
**假阴性比报错严重得多**：报错用户会改，假阴性用户会**信任它**，然后在现场翻车。

> **统一修法（约 20 行，建议单独立卡）**：
> 引入 `UnmappedTime` 信号——展开结果为"有时间段但无掩码"时**必须返回一个标记**，
> 由上层决定是**拒绝保存**还是**降级为区间重叠判断并告警**。
> 配套断言：**任何一次 `scan()` 都必须能说出"我跳过了几条、为什么"**（返回 skipped 计数）。

## 3. 🟠 P1 严重问题

### P1-1 容量约束：代码写成"硬"，队长定的是"软"

| 来源 | 定性 |
|---|---|
| `AGENTS.md §9c`（队长 2026-09-25 定） | 容量不足 = ⚠️ **软（警告）**，计入代价、**不阻止** |
| `constraints.py:92-100`（实际代码） | 容量不足写进 `hard_violations` → 🔴 **硬，直接排除方案** |

代码与队长决定**相反**。后果：一个 50 人的班被排进 40 人教室时，
队长要的是"给警告 + 给方案让用户选"，代码给的是"这个方案根本不出现"。

> **修法**：把容量从 `hard_violations` 移到 `soft_cost`；
> 或按 docs/14 E3 做成 `capacity_mode = hard|soft` 配置项（**更符合 §1b 规则数据化**）。

### P1-2 `exclude` 是死参数（3 处声明，0 处使用）

`constraints.py` 有三个函数都声明了 `exclude: set[str] | None = None`，
注释写着"需要忽略的日程 id（例如**正在被移动的那条本身**）"，
函数体里只有 `exclude = exclude or set()` —— **之后再没出现过**。

`m2.py` **也没有传**（它改用 `free_on(d, exclude_self_mask)` 自行减去掩码绕过）。
所以目前靠调用方绕开，**功能没坏，但坑留着**：下一个人看到 `exclude` 参数会以为它能用。

> **修法**：要么在 `hard_violations`/`soft_cost` 里真正实现 `exclude`（推荐，因为
> `soft_cost` 的自污染只能靠它修），要么**删掉这个参数**并改注释。不要留着不动。

### P1-3 `soft_cost` 把自身算进占用（自污染）

`soft_cost` 读的是 `ctx.occupancy`，而 `ctx.occupancy` **包含被评估日程自己的占用**：

```python
before = popcount(ctx.occupancy.get((oid, day), 0))   # ← 含自身
if before + n > ctx.daily_limit:                       # 单日上限被自身课时顶爆
merged = mask | ctx.occupancy.get((object_ids[0], day), 0)   # ← 含自身
if merged & neighbour and not (mask & neighbour):     # 自己跟自己"连堂"→ 白送奖励
```

后果：**每条日程都被自己的课时数惩罚一次**，且"原地不动"会被误判成"连堂成功"拿到负代价。
这会直接污染 M2 的方案排序 → **推荐给用户的"最优方案"可能不是最优**。

> **修法**：`soft_cost` 内部计算前先减去 `exclude_self_mask`（即把 P1-2 的 `exclude` 真正实现）。

### P1-4 `apply_plan` 不更新 `updated_at` → 客户端轮询看不到消解结果

`m2.py:383-424` 的 `apply_plan` 直接 `UPDATE schedule_once / schedule_periodic`，
**既不调 `schedules.touch()`，也不改 `schedules.updated_at`**，最后只 `conn.commit()`。

而 docs/11 的客户端同步设计依赖"按版本号/更新时间轮询"。
→ **一键消解写库成功，但客户端版本号没变，教师刷新页面看不到任何变化。**

> 这是**端到端链路断裂**，属于"每层都能通、合起来不通"的典型。
> **修法**：`apply_plan` 末尾对所涉 `schedule_id` 调 `touch()`（并注意 P3-4：touch 自己不 commit）。

### P1-5 性能：全学期扫描 125 万条目 / 约 239MB，一键消解约 50 次全量重建

**🔬 实测（32 班 × 47 人 ≈ 1500 人，1280 条周期日程）**：

| 扫描范围 | 占用条目 | 耗时 | 估算内存 |
|---|---|---|---|
| 1 周 | 61,440 | 0.12 s | ~12 MB |
| **1 学期（20 周）** | **1,253,376** | **1.50 s** | **~239 MB** |

**放大倍数的来源**（`occupancy.py:262-273`）：一个"班级"参与者会被展开成
**1（组自身）+ 47（全部成员）** 条占用 → **×48**。

**一键消解的代价**：`resolve_and_apply` 每一轮调用 `resolve()`（1 次 `build_occupancy`）
+ 第 375 行再算一次（1 次）= **每轮 2 次全量重建**；最多 24 轮 → 48 次，
另加循环外首尾各 1 次，**合计约 50 次** → **50 × 1.5 s ≈ 75 秒**，峰值内存 239 MB。

> ⚠️ **部署风险**：记忆中本项目要部署在**轻量云服务器**（通常 1–2 GB）。
> 239 MB 常驻 + Python/SQLite 开销，在 1 GB 机器上**有 OOM 风险**。

**改进方向（按性价比排序）**：
1. ⭐ **不要"写时下卷"，改"读时上卷"** —— 不再把组展开成 47 条成员条目，
   而是查某对象占用时 `OR` 上它所有祖先组的掩码。
   **条目数直接降到 1/48**（125 万 → 约 2.6 万），这是**架构级**的优化，最值得做。
2. **默认限制扫描窗口**（如 ≤2 周），全学期扫描走异步/分页。
3. **`expand_groups` 在大扫描时默认关闭**（代码里已经有这个开关，但 `scan()` 没暴露）。
4. 一轮内复用同一份 `entries`，别每轮重建两次。

### P1-6 `busy_mask` / `load_of` / `total_load` 是 O(n) 地雷

三个 helper 都是**遍历全部 entries 的线性扫描**（`occupancy.py:311-353`），
而它们的典型用法是"对每个对象/每天调一次"：
```python
total_load(entries, teacher_id)   # 每位教师调一次
    → load_of(entries, ...)       # ← 每次都全量扫一遍 entries
```
150 位教师 × 125 万条目 = **1.9 亿次迭代 → 分钟级**。

> **修法**：`occupancy_map()` 已经生成了 `{(对象, 日期): 掩码}` 索引，
> 这三个函数应改成**查索引**而不是扫列表。约 15 行，收益巨大。

## 4. 🟡 P2 安全与耦合

### 安全

| # | 问题 | 现状 | 改进方向 |
|---|---|---|---|
| **S1** | **领域层零鉴权** | `get_schedule(conn, id)`、`delete_schedule(conn, id)` **都不带 `org_id` 过滤** → 典型 IDOR：拿到任意 schedule id 就能读/删 | 所有读写入口**强制**以 `org_id` 为第一等参数（与 docs/15 §3「鉴权装饰器」合并落地） |
| **S2** | `authenticate` 返回含 `password_hash` 的 `dict(row)` | 一旦被写进 JSON 响应或会话 cookie 就是明文哈希泄漏 | 返回前 `pop("password_hash")`，或返回专用 dataclass |
| **S3** | 无登录失败限流/锁定 | 公网暴露的轻量云服务器可被爆破 | 登录失败计数 + 指数退避；演示环境至少加日志 |
| **S4** | pbkdf2 100k rounds | 可用，但低于当前 OWASP 建议（600k） | 演示环境可接受；若要上公网，提到 300k+ 并测登录耗时 |
| **S5** | 无会话/令牌机制 | 尚未建（`src/server` 0 行） | 设计时必须：HttpOnly + SameSite cookie，服务端会话表，登出即失效 |
| **S6** | `delete_object` / `remove_edge` 无 org 校验 | 可跨组织操作 | 同 S1，纳入统一鉴权装饰器 |

> ✅ **做得好的**：`hash_password` 用 `pbkdf2_hmac` + `os.urandom(16)` 随机盐；
> `verify_password` 用 `hmac.compare_digest`（**常量时间比较，抗时序攻击**）；
> 全部 SQL 参数化（**无 SQL 注入**）；`add_edge` 有防环。
> 这四项在零依赖约束下做得相当到位，答辩可以正面讲。

### 耦合与数据流

**当前数据流**（合理）：
```
period_slots/terms/exceptions ─┐
schedules + 扩展表             ├→ expand_*() → OccupancyEntry[] → find_conflicts() → Conflict[]
object_edges（闭包）           ─┘        （统一为「(日期, 当天掩码)」）
```
✅ **这个归一化是本架构最大的优点**，课表与活动共用一套位运算，是真正做对了的决策。

**耦合问题**：

| # | 问题 | 后果 |
|---|---|---|
| **C1** | `sqlite3.Connection` 与 `sqlite3.Row` **贯穿所有层** | 领域层无法脱离数据库做单元测试；换存储要改所有签名；`Row` 泄漏到返回值让类型无从约束 |
| **C2** | `build_occupancy` 把 SQL 查询写在循环里（N+1） | 每条日程 2 次查询 + 每个参与者 1 次查 kind + 每个组 1 次查成员。1280 条日程 → **数千次查询** |
| **C3** | `solver` 直接 import `occupancy` 的 `expand_once`/`expand_periodic` | 求解器依赖"展开"的内部实现，而不是依赖"占用矩阵"这个抽象 → 展开逻辑一改，求解器跟着动 |
| **C4** | `schedules.py:144` 用 f-string 拼 `IN (?,?,?)` | 参数仍是占位符（**安全**），但拼串方式脆弱，易在后续改动中退化 |
| **C5** | 领域层同时是持久层 | 没有 repository/service 边界；`create_*` 直接 commit，跨天活动要调两次 `create_once` → **两条记录不原子** |

> **改进方向（不必现在做，但要记着）**：
> C1/C5 建议引入**薄仓储层**：领域函数接收 `SlotConfig`/`Term`/`entries` 等**纯数据**，
> 而不是 `conn`。这与"零依赖"不冲突，而且能让求解器可独立测试。
> **但按 docs/15 §7 的外脑判定——MVP 不要为此加抽象层**，只在新写接口时**不要再让 `conn` 继续往下传**。

## 7. 我认为架构做对了的部分（答辩可讲）

1. **课表与活动归一化到同一套「(日期, 掩码)」** —— 这是真问题（"排课看不见活动而撞车"），
   也是真解法，不是为 AI 而 AI。
2. **位序固定 `(周几−1)×16+(节次−1)`** —— 配置怎么改，历史掩码都不会错位。这是有远见的一笔。
3. **对象 ≠ 账号的两层解耦** —— 让 1500 学生可调度但不需发账号，绕开了"初始密码怎么发到学生手上"这个无解问题。
4. **DAG + 闭包表，允许多父** —— 学生同时属班级与社团，不需要任何特判。
5. **零第三方依赖 + 全参数化 SQL + 常量时间口令比较 + 防环** —— 在"断网可跑"的硬约束下，
   安全基本功做得很扎实。
6. **软约束用"代价"而非布尔** —— 天然支持多目标权衡，是求解器能讲清楚的关键。
