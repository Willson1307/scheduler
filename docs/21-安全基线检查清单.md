### 0.3 🔴 验收纪律（贯穿 §1–§6）

1. 🔴 **一律用非管理员账号走一遍完整流程。** `admin → 全组织短路`（`authz.py:139`）会让
   管理员一切正常、教师全部为空 —— 本项目最贵的一类 bug 的共性成因。
2. 🔴 **`Ran 0 tests` + `OK` 一律视为失败。** 已复发 2 次（起服务用 `nohup &`，进程被回收）。
   正确做法：用常驻后台方式起服务。curl 返回 502 是代理伪装，urllib 返回 10061 才是真拒绝。
3. 🔴 **新增检查项必须证明它会红**（注入一个缺陷看它报警）。没红过的检查等于没有检查。
4. 🔴 **验收必须确认 `skipped=0`，不能只看 `Ran N`。** 裸跑 `python -m unittest discover -s tests`
   输出 `Ran 292 ... OK (skipped=1)`—— 这个 `skipped=1` 是 **test_contract 整个模块被跳**，
   实际漏掉 **17 项**契约断言（模块级 skip 只计 1，`Ran 292` 里根本没包含这 17 项）。
   `OK (skipped=1)` 与 `OK` 长得极像，是第 2 条 `Ran 0 tests` 的更隐蔽一版「跑了一半」。
   三态判定：`Ran 0 tests` ❌ / `Ran N + skipped>0` ❌ / `Ran N + skipped=0` ✅。

**正确跑契约测试（契约测试必须连到已启动的服务，否则整体 skip）**：

| 方式 | 命令 | 说明 |
|---|---|---|
| A · 起服务（默认 8000 端口） | `python scripts/reset_demo.py` → `python scripts/run_server.py --port 8000 --today 2026-10-12`（常驻后台）→ `python -m unittest tests.test_contract -v` | 用默认 `BASE_URL=http://127.0.0.1:8000`（`test_contract.py:37`） |
| B · 起服务 + 指路 | 服务起在别的端口，再 `SCHEDULER_BASE_URL=http://127.0.0.1:<port> python -m unittest tests.test_contract -v` | 🔴 `SCHEDULER_BASE_URL` 只是「指向已启动服务」的地址，**不能替代起服务**（skip 判据 = `GET /api/health` 连不上，`test_contract.py:113-127`） |

实测口径（2026-10-18）：

| 条件 | 结果 |
|---|---|
| `python -m unittest discover -s tests`（裸跑，未起服务） | **292, OK (skipped=1)** ← 契约模块整体 skip |
| 起服务后 | **309, OK, skipped=0**（= 292 + 17 项契约） |

🔴 **全量验收若看到 `skipped > 0`，先判断是不是契约模块因没起服务被跳**，
再决定要不要起服务重跑。**不要带着 `skipped>0` 的「OK」宣布验收通过。**

## 1. 🔴 B2 鉴权代码人工复核（降档专项，交付当场逐条核）

> **为什么这节必须人工逐条核**：B2 权限层的鉴权代码由 **GLM-5.2 生成**
> （GLM-5.3 因平台封禁不可用，同族小版本降档，已获队长批准——理由：同族 5.2→5.3 属代内
> 版本差距，语义一致性优于跨族 V4-Pro）。**降档的原始风险点 = 生成代码的鉴权语义可能带偏**
> → 这 5 项缺一不可，任何一项拿不出证据即判「B2 未通过」。

### 1.1 越权路径（IDOR）—— 非 admin 能否改 URL 参数访问他人数据

- [ ] **B2-1 · 越权访问被拦截**
  - 检查命令：
    ```bash
    python -m unittest tests.test_server_api -v          # 看越权用例是否真实跑且断言 403/404
    grep -n "org_id" src/server/api_*.py                # 每个 handler 是否都带 org_id 过滤
    ```
  - 判定标准：
    - **通过** = 用「低档账号」改 URL 里的 `object_id` / `schedule_id` / `group_id` 访问他人组织数据，一律返回 **403 或 404**，响应体**不含任何他人数据字段**；
    - **不通过** = 任一接口能用他人 id 读到 / 改到 / 删到数据，或只在前端隐藏、后端不拦。
  - 覆盖缺陷：**P2-1**（`schedules.py:110,150` 两接口无 org 过滤，典型 IDOR）。

### 1.2 缺省组判定 —— 是否用 `parent_name is None` 而非 `min(level)`

- [ ] **B2-2 · 缺省组判据正确**
  - 检查命令：
    ```bash
    grep -n "parent_name\|MIN(level)\|min(level)" src/scheduler/authz.py
    ```
  - 判定标准：
    - **通过** = 源码里缺省组判定用 `parent_name IS NULL` / `parent_name is None`（根组无父节点）；
    - **不通过** = 出现 `MIN(level)` / `min(level)` 当缺省组判据（层级深度在 `object_edges.depth`，**不在** `group_roles.level`，用 min(level) 会判错）。

### 1.3 多路径继承 —— 同一对象经多条祖先链时是否取最高档

- [ ] **B2-3 · 多路径取最高档**
  - 检查命令：
    ```bash
    grep -n "MAX(level)\|max(" src/scheduler/authz.py
    python -m unittest tests.test_authz -v               # 必须含多父 DAG 用例
    ```
  - 判定标准：
    - **通过** = 继承取 **MAX(level)**，且测试覆盖「同一对象经多条祖先链」场景（如成员同时属班级与社团，`groups_of` 多条、祖先深度 `{2,1,1}` 类场景），最终档位 = 各路径最高档；
    - **不通过** = 只取第一条路径、或取 min、或没有多父用例。

### 1.4 `password_hash` 是否绝不出现在 `/api/login` 响应体里

- [ ] **B2-4 · 口令哈希零回传**
  - 检查命令：
    ```bash
    grep -n "password_hash" src/server/*.py            # 确认 login handler 已 pop 掉该字段
    # 实测：登录成功后打印/检查 JSON 响应体，字段列表里不得出现 password_hash
    ```
  - 判定标准：
    - **通过** = `/api/login` 成功 / 失败响应体里**均无** `password_hash` 字段（`authenticate` 返回值已 `pop("password_hash")` 或改用专用结构）；
    - **不通过** = 响应或会话里出现该字段（覆盖缺陷：**P2-2**，`object_graph.py:295`）。

### 1.5 commit message 是否写明「由 GLM-5.2 生成」及降档原因

- [ ] **B2-5 · 降档溯源可答**
  - 检查命令：
    ```bash
    git log --oneline -20 | grep -i "B2\|authz\|鉴权\|GLM"
    ```

  - 判定标准：
    - **通过** = B2 鉴权相关 commit 的 message 里**写明了「由 GLM-5.2 生成」+ 降档原因**（GLM-5.3 平台封禁、同族代内降档、队长已批准）；
    - **不通过** = commit 里无任何溯源说明 → 评委问「这段谁写的」时答不清，判 B2 未通过。

## 5. 静默失效专项排查（本项目最贵的 bug 类型：不报错却给错误结果）

> 静默失效 = 「算不出 / 查不到时悄悄 `continue`，不告诉任何人」→ 系统**假阴性**（说有没冲突）。
> 假阴性比报错危险：报错用户会改，假阴性用户会**信任它**并在现场翻车。**每项必须验「修复确实落地 + 有回归断言」。**

## 5.5 🔴 doctor 自身的判红失效（2026-10-11 修复，`c807638`，已合main）

**这不是"某项检查没做"，而是"doctor 红了也没人知道"** ——
本项目里最隐蔽的一种自检失效，因为它坏的是**兜底本身**。

### 祖传 bug：`_summary` 判红误用 `c[0]`

```python
# 修复前：CHECKS 里每项是 (name, ok, detail)，name 恒为真字符串
failed = [c for c in CHECKS if not c[0]]   # ← c[0] 是 name，永远真
```

后果：无论多少项FAIL，`failed` 恒为空 → 照样打印
「体检结果：N/N 项全部通过 ✅」且 **exit 0**。
**上游 CI / 脚本 / 人都拿它当放行闸门。**

修复后改为 `not c[1]`（ok 位）。

### 同一提交新增：业务路由可达自检（14 → 15 项）

`routes.scan()` 只能看见**已注册**的路由。若某个 `api_*.py`
**整个没合进 main**（B4 的 `/api/resolve` 就是这么丢的），
遍历现存表永远查不出缺失。

故新增 `EXPECTED_ROUTES` 显式期望清单 + 两层判据：
① 期望清单 ⊆ 现存表；② 逐路由打真实 HTTP 断言**非 404**
（401/403/400/405 都算已挂载）。

> 🔴 **新增 API 时必须同步 `EXPECTED_ROUTES`**（同 `ASSET_VERSION` 的同步约定）。
