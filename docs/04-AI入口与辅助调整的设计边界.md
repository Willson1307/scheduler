# AI 入口与"辅助调整"的设计边界

> 起因：队长提出"求解环节可以调用 AI——给出需求，辅助调整"。
> 结论：**同意，而且这本来就该做**。我原来的表述"求解环节不调用大模型"用得太宽，
> 需要修正：我真正要禁止的只有其中一步，不是全部。

---

## 一、先纠正我自己的表述

"求解"这个词其实包含三步：

| 步骤 | 做什么 | 该不该用大模型 |
|---|---|---|
| ① 理解需求 | "帮我把周三上午的课挪开" → 结构化约束与参数 | ✅ **该用**（这正是大模型强项） |
| ② 搜索计算 | 在约束空间里算出满足硬约束的方案 | 🔴 **不该用**（这是求解器的活） |
| ③ 解释与微调 | 把方案说成人话、按偏好排序、按反馈再调整 | ✅ **该用**（但要过校验） |

我说的"求解环节不调用大模型"，准确含义是 **第 ② 步不让大模型算**，
**不是**说第 ①③ 步不能用。第 ①③ 步用大模型，反而让作品更像"AI 作品"。

## 二、新的三层分工

```
用户（自然语言）
   │  "把周三上午的物理课挪开，别动语文"
   ▼
① 需求理解（大模型）        ← B7：temperature=0 + 强制 JSON + 失败降级
   │  输出：{模式: M2, 目标: 周三第1节物理, 约束: 不动语文}
   ▼
② 求解计算（自建求解器）    ← B4 已完成，确定性、可复现、能保证硬约束
   │  输出：3 个候选方案 + 各自代价
   ▼
③ 解释与辅助调整（大模型）  ← 把方案翻成人话、按用户偏好排序
   │  ⚠️ 若 AI 主动提议新改法 → 必须回送 ② 校验
   ▼
用户确认 → 写回数据库
```

### 关键机制：**AI 提议 → 求解器校验 → 才展示**

这是"辅助调整"能安全落地的唯一方式：

- 大模型可以提议"把物理课挪到周四第 3 节"；
- 但这个提议**不能直接写库**，必须先过一遍硬约束与冲突检测；
- 校验通过才展示给用户，不通过就驳回（可以让 AI 重试一次，或直接只给求解器的方案）。

这样：
- AI 的灵活性用上了（能听懂"别动语文""尽量上午"这类软要求）；
- 正确性仍由求解器兜底，现场可以理直气壮说"展示的方案一定满足所有硬约束"。

> 一句话：**让 AI 提想法，让求解器做裁判。**

## 四、两个新增风险（必须处理）

### 🟡 风险 1：演示稳定性（"现场断网"已排除）

> **更新（队长确认）：现场可以连接网络，演示没问题。**
> 所以 AI 入口**可以做进演示主线**，不必只当花瓶。

但风险没有消失，只是换了形式——现场依赖外部 API 有三类具体故障：

| 故障 | 后果 | 防法 |
|---|---|---|
| 网络延迟 / 超时 | 演示卡顿，5 分钟不够用 | 现场**预跑一次并缓存结果**；超时直接走手动模式 |
| API 配额耗尽 / key 失效 | 当场报错 | 演示前查配额；准备备用 key；章程规定 API 资源团队自备 |
| 模型返回不合规 | 参数抽错、方案离谱 | temperature=0 + 强制 JSON + 校验失敗降级到手动选模式 |

三条硬要求：

1. **核心流程不依赖 AI**：手动选模式 + 求解器这条路必须完整可用（这条不变）；
2. **AI 入口必须有降级路径**：识别失败 / 超时 → 自动退回手动，不能卡死；
3. **断网备用方案仍要准备**：模板明确写"准备一个断网也能跑的本地演示方案"，
   这是章程的演示要求，与现场是否有网无关——评委可能专门问这一条。

### ⚠️ 风险 2：数据出校

调外部 API = 数据要发出去。课表是校内公开信息，但**学生名单不是**。

应对：
- 只把**结构化的约束与参数**发给模型（"周三第 1 节、物理、高一(1)班"），
  绝不发真实姓名、学号、联系方式；
- 这一点要写进项目书的"数据合规"一节。

## 五、答辩话术（更新版）

> 问：你的 AI 模型是训练的，还是调用现成接口？
>
> 答：**两层都用了，分工不同。**
> 核心的排布求解是我们**自己写的约束求解器**——回溯搜索加前向检查和 MRV 启发式，
> 硬约束保证百分之百满足，软约束的权重从本校公开的往期课表统计学习得到（w = −ln(1−p)）。
> 大模型用在**交互层**：听懂老师说的话、把它翻译成约束条件，以及把求解结果解释成人话。
> 而且大模型给出的每一条调整建议，都会**回送到我们自己的求解器校验**，
> 不满足硬约束的建议会被直接驳回——所以展示出来的方案一定是对的。

这个答法比原来更好：既展示了自建 AI 内核，又展示了对大模型的合理运用，
还多了一个"AI 提议 + 求解器校验"的设计亮点。

## 六、落地顺序（受"先搭基础框架"约束）

| 顺序 | 内容 | 状态 |
|---|---|---|
| 1 | 打通端到端闭环（启动→页面→冲突→一键消解） | 🔴 当前阶段，先做这个 |
| 2 | 手动选模式 + 求解器 | 随闭环一起 |
| 3 | **需求理解层**（自然语言 → 约束参数） | 闭环跑通后**紧接着做**（现场有网，值得排进主线） |
| 4 | **解释与辅助调整层**（AI 提议 → 求解器校验） | 再下一步 |
| 5 | 降级路径 + 断网备用 + 预跑缓存 | 10 月中，和演示脚本一起 |

**现在不动第 3、4 步**——先把第 1 步跑通，AI 入口才有地方挂。
但优先级从"有余力才做"上调为"闭环跑通后紧接着做"。
