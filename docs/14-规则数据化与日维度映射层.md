# 规则数据化 + 日维度映射层（Calendar Profile）

> 日期：2026-09-25 ｜ 起因：**队长批评「你的想法违背了灵活性原则，如果真的灵活不需要关心你问的阻塞项」**
> **这条批评成立。本文件是对此前设计思路的修正，不是补充。**

---

## 0. 我错在哪

此前我的做法是：遇到不确定的学校规则 → **列为 to-confirm → 等确认 → 按确认结果建表**。

这是错的，错在三处：

1. **把"本校当前的做法"当成了系统的假设**。一旦写进代码或表结构，换所学校就得改代码。
2. **用"问"代替"建模"**。真正灵活的系统的回答不是"你们学校是顺延还是跳过？"，
   而是**"两种都能表达，你填一下就行"**。
3. **每来一个规则加一张表** —— `calendar_exceptions` → `calendar_exceptions_ext` →
   `slot_sets` + `slot_set_periods` + `slot_set_schedule` → `schedule_exceptions`……
   **已经 6 张补丁表**，这不是灵活，这是打补丁。

---

## 1. 新原则：规则数据化（🔴 写进 AGENTS.md）

> **凡是"不同学校/不同组织可能不一样"的规则，一律落为数据行或配置项，
> 不得写进代码，也不得靠"先问清楚再实现"。**
> 默认值取本校当前认知，但**必须可改**，且改了不用动代码。

这条原则的直接后果：**绝大多数 to-confirm 不再是阻塞项**，
它们退化为"填默认值时要填什么"，可以边做边定。

**符合这条原则的例子**：单双周基准、每天节数、作息版本、末节定义、容量、权重、权限档位。
**不符合的反例**：把"放假后教学周顺延"写成 `if holiday: week_no += 1`。

---

## 2. 核心设计：两张表取代六张补丁

### 2.1 `calendar_days` —— 日维度映射（唯一的一张校历表）

```sql
CREATE TABLE calendar_days (
    org_id        TEXT NOT NULL,
    date          TEXT NOT NULL,          -- ISO 日期
    profile_id    TEXT,                   -- 这天用哪套作息（节次时刻）；NULL = 用默认
    teach_week_no INTEGER,                -- 第几教学周（1..N）；NULL = 非教学日
    teach_dow     INTEGER,                -- 按周几的课表上课（1-7）；NULL = 这天不上课
    kind          TEXT NOT NULL DEFAULT 'normal',  -- normal/holiday/makeup/exam/special
    note          TEXT,
    PRIMARY KEY (org_id, date)
);
CREATE INDEX idx_calendar_days_range ON calendar_days(org_id, date);
```

### 2.2 `day_profiles` —— 作息模板（取代 `slot_sets` 三张表）

```sql
CREATE TABLE day_profiles (
    id              TEXT PRIMARY KEY,
    org_id          TEXT NOT NULL,
    name            TEXT NOT NULL,        -- 夏季 / 冬季 / 考试周 / 运动会
    periods_per_day INTEGER NOT NULL DEFAULT 10,   -- ← 末节由它派生（自动解决 N8）
    is_default      INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE day_profile_periods (
    profile_id TEXT NOT NULL REFERENCES day_profiles(id) ON DELETE CASCADE,
    idx        INTEGER NOT NULL,          -- 第几节（不按周几）
    name       TEXT,
    start_time TEXT NOT NULL,
    end_time   TEXT NOT NULL,
    PRIMARY KEY (profile_id, idx)
);
```

### 2.3 一个配置项（而不是硬编码）

| 配置项 | 取值 | 解决什么 |
|---|---|---|
| `parity_basis` | `teach_week`（默认）｜`calendar_week` | **单双周按教学周还是自然周——两种都要能选**，这才是不用问的原因 |

---

## 3. 它如何一举覆盖此前所有"特殊场景"

| 场景 | 此前方案 | 现在怎么表达 | 代码改动 |
|---|---|---|---|
| **调休补课**（周六按周一课表） | `calendar_exceptions_ext.as_of_dow`（A1，未实现） | 该周六填 `teach_dow=1` | 0 |
| **放假后教学周顺延** | 需要问学校才知道怎么做 | `teach_week_no` 照常递增 | 0 |
| **放假后跳过不顺延** | 同上 | 该周 `teach_week_no` 不递增 | 0 |
| **单双周按教学周 / 自然周** | 需要问学校（N1） | 改 `parity_basis` 配置项 | 0 |
| **夏冬季作息** | `slot_sets` 三张表 | `profile_id` 换一个 | 0 |
| **考试周 / 运动会** | 又一套机制 | `profile_id` + `kind='exam'` | 0 |
| **节假日停课** | `calendar_exceptions`（已有） | `teach_dow=NULL` | 0 |
| **末节定义随季节变**（N8） | 硬编码第 16 节 | 由 `periods_per_day` 派生 | 0 |
| **周末有课** | 靠 `enabled=1` | `teach_dow` 照填，与是否周末无关 | 0 |

> **关键：这些此前各自要建表、各自要问学校的场景，现在全是同一张表的不同填法。**

---

## 4. 向后兼容（🔴 必须做到，否则推翻重来代价太大）

1. **位号公式不变**。位号仍然按 `teach_dow`（周几语义）计算 → **所有已存掩码全部有效，无需迁移**。
2. **默认生成器**：若某日期在 `calendar_days` 里查不到，按默认规则推导
   （`teach_dow = isoweekday()`、`teach_week_no` 从学期起点算、`profile_id = 默认作息`）。
   → **不填任何数据，行为与现在完全一致，31 项老测试全绿。**
3. `period_slots` **保留**（它管"周几第几节是否启用"），与 `day_profiles`（管时刻）分工。
4. `schedule_exceptions`（临时微调 cancel/move）**保留**——它是**单条日程级**的，
   与 `calendar_days`（**整天级**）粒度不同，不该合并。

## 5. 补丁表的处置

| 原方案 | 处置 |
|---|---|
| `calendar_exceptions` | 保留（已有，且 `holiday` 已生效）；长期改用 `teach_dow=NULL` 表达 |
| `calendar_exceptions_ext` | ❌ **不建**（被 `calendar_days` 取代） |
| `slot_sets` + `slot_set_periods` + `slot_set_schedule` | ❌ **不建**（被 `day_profiles` + `calendar_days.profile_id` 取代） |
| `schedule_exceptions` | ✅ **保留**（单条日程级，粒度不同） |
| `data_revision` | ✅ 保留（客户端同步用，与校历无关） |

**净效果：从 6 张补丁表降到 3 张（calendar_days、day_profiles、day_profile_periods），
且后两张可合为一个逻辑单元。**

## 6. 还剩下的真依赖（诚实列出）

规则数据化之后，**只剩一条**真阻塞：

| 依赖 | 为什么不能靠配置解决 |
|---|---|
| **往期课表数据**（权重学习） | 这是**数据**不是规则。没有历史课表就无从统计——配置解决不了"没有输入" |

其余（夏冬具体日期、有无考试周、单双周基准、放假是否顺延）**全部退化为"填默认值"**，
不阻塞任何开发。

## 7. 实现路径与 MVP 范围

| 阶段 | 内容 | 何时 |
|---|---|---|
| **MVP** | 建 `calendar_days` + `day_profiles` 两张表；`expand_periodic` 查表并**带默认回退**；种子数据按默认规则生成 | 主线闭环**之后**，10/4–10/5 |
| **同期** | 前端提供「校历」页面：按周批量填 `teach_dow` / `teach_week_no` / `profile_id` | 10/5–10/6 |
| **二期** | 批量导入校历（CSV）；`parity_basis` 配置项暴露到组织设置 | 二期 |

**MVP 为什么可以延后**：因为**默认生成器保证不填表也完全能跑**，
10/7 可试用、10/23 现场演示都不依赖它。它带来的是"可推广性"，不是"能跑"。

> 这与队长的定位一致：仓库叫 `scheduler` 不叫 `school-scheduler`，
> 模型不绑定学校场景 —— **校历层正是"不绑定"的那一层**。

## 9. 🔍 反扫：现有代码里违反本原则的地方（2026-09-25 晚自查）

用 §1b 反扫现有代码，发现**求解器的"规则层"恰好是硬编码最集中的地方**——
而它恰恰是最该可配置的。这印证了你的批评：不灵活的根源不止在校历。

### 9.1 软约束默认值写死在代码里（🔴 直接违反 §1b）

`src/scheduler/solver/constraints.py` 的 `SolverContext`：

| 位置 | 硬编码 | 问题 | 应改为 |
|---|---|---|---|
| `:44` | `daily_limit: int = 6` | "每天 6 节上限"是**本校认知**，换所学校就错 | 从 org 配置表加载 |
| `:45` | `avoid_last_period: bool = True` | "主科不排末节"是不是规则，各校不同 | 配置项 |
| `:46` | `prefer_continuous: bool = True` | "偏好连堂"是不是规则，各校不同 | 配置项 |
| `:47-50` | `w()` 缺省返回 `1.0` | 无任何"读配置/读学习权重"的入口 | 从配置或 `weights.json` 加载 |

> 这些是**伪配置**：虽然写成 dataclass field 看起来"可改"，但**没有任何配置入口**，
> 实际没人能改 = 等价于写死。判定方法仍是 §1b："换所学校这条会不会不一样？"
> —— 会，所以它们都该落为配置。

### 9.2 种子数据的硬编码（🟠 演示数据，优先级低）

`seeds.py`：教室容量写死 `50`（`:79`）、学期写死 `20 周`（`:49`）、
演示课时刻写死 `08:00–09:40`（`:154-155`）。**演示场景可控，可接受**；
但若将来用种子做真实试用组织的初始数据，这些就该参数化。

### 9.3 性能开关会牺牲正确性（🔴 此前已发现，补档）

`occupancy.py:268` 的 `expand_groups=False` 会**关掉"组→成员"的展开**，
多父场景下（学生同属班级+社团）跨组冲突将**漏检**。
这是为了 1500 人规模做的性能权衡，但**牺牲了正确性**。
→ 处置：① 该开关**不得默认关闭**；② 若开启，必须在文档里标注
「已降级为组级检测，会漏个人级冲突」；③ 大组织应优先靠**分治**（按组织树拆段）而不是关掉展开。

| 类型 | 数量 | 处置 |
|---|---|---|
| 🔴 违反 §1b（规则硬编码） | 4 处（daily_limit / 两个开关 / 权重入口） | **新建 `org_settings` 配置表**，`SolverContext` 从它加载 |
| 🟠 演示数据硬编码 | 3 处 | 可接受，试用组织数据生成时参数化 |
| 🔴 正确性降级 | 1 处（expand_groups） | 写约束 + 分治替代 |
