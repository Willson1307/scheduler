# 横切关注点与统一管道（架构缺陷评审）

> 日期：2026-09-25 ｜ 起因：队长问「此架构是否还有缺陷？」
> **结论：还有 6 处，而且它们的根因是同一个——四类「横切关注点」没有抽象层。**
> 其中 3 处**已经在今天的设计里真实发生**（`data_revision` 就是受害者）。

---

## 1. 什么是「横切关注点」

它们不属于任何单个功能，却要被**每个**功能重复处理：

| 横切关注点 | 现状 | 不抽象会怎样 |
|---|---|---|
| **写操作的副作用**（版本号 / 审计 / 乐观锁） | 每处各写各的 SQL | 加一样就要改**所有**写路径 |
| **读操作的可见性过滤**（组闭包权限） | 靠"每个 API 记得做" | 漏一个 API ＝ 数据泄露 |
| **时间来源** | 有的用 `datetime('now')`(UTC)，有的用 `datetime.now()`(本地)，有的用 `date.today()` | 时区错乱、现场跨周空白 |
| **错误语义** | 抛 `ValueError` / 返回 `list[str]` / 返回空列表 三种风格混用 | 服务层漏映射 → 该 400 的变成 500 |

---

## 2. 六处具体缺陷

### 🔴 D1 没有统一写入管道（**已真实发生**）

`docs/11` 定了 `data_revision`：**每次写操作 `rev + 1`**。我当时自己写下过一句警示：

> 「`rev + 1` 要散落在所有写路径里。等 API 全写完再补，要回头改十几个文件且极易漏掉某条路径
> （漏掉的那条就是"改了但页面不刷新"的玄学 bug）。」

现在审计（配置变更留痕）、乐观锁（N4 记录级并发）也要挂上去 —— **三件事同样散落**。
**根因：没有统一的写入入口。**

### 🔴 D2 可见性过滤靠"每个 API 记得做"

`build_occupancy` 只按 `org_id` 取数据；"我能看哪些组"是服务层的事。
`T3` 卡里写的是"服务层对 `Plan.moves` 按可动集合过滤"——**这是逐处实现的**。
**漏一个读接口就是一次越权泄露**，而这是安全项，不能靠"记得"。

### 🔴 D3 领域层「只读红线」正在贬值

`AGENTS.md` §3 原话是**"现有文件只读，一行都不得改"**。但今晚已经批了
**3 处 E2**（`occupancy.py` 展开 / `schema.sql` 追加 / `m2.py` 新增函数），
A6 修法还要再批一处 —— 红线被反复突破后，**队员会认为它可商量**，约束力归零。

### 🟠 D4 没有统一时间源

| 位置 | 用的是什么 | 问题 |
|---|---|---|
| `schema.sql` DEFAULT | `datetime('now')` → **UTC** | 存的是 UTC |
| `schedules.py:158` | `datetime.now()` → **本地** | 同一字段两种基准，差 8 小时（V2） |
| `seeds.py:48` | `date.today()` | 现场时间不可控（N2） |

**根因：没有 `clock` 抽象**。修法是"有一个 `now()` 函数，所有地方都从它取"，
演示时注入固定日期（N2 的 `--date` 也靠它）。

### 🟠 D5 类表继承的原子性无强制（V3 的架构版）

`v_schedule_full` 是 **INNER JOIN** → 基础表有行、扩展表缺行时，该日程**静默消失**。
SQLite 表达不了"两张表必须同时有行"的约束，只能靠**应用层封装 + 测试**保证。
**根因：类表继承缺一个"写入即两条"的统一封装。**

### 🟠 D6 错误语义没有分层定义

领域层现在三种风格并存：
- `add_edge` 建环 → **抛 `ValueError`**
- `hard_violations` → **返回 `list[str]`**（空列表=没违规）
- `m2.resolve` → **返回 `[]`**（无方案）

服务层要把这三种都映射成 400/409/404/500 —— **逐处判断必然遗漏**。
**根因：没有约定"领域层怎么表达失败、服务层怎么映射"。**

---

## 3. 统一解法：在服务层与领域层之间加一层「应用服务 / 工作单元」

```python
with unit_of_work(conn, org_id, actor) as uow:
    uow.perform(change)     # 写：统一做 rev+1、写审计、校验版本号
    rows = uow.read(query)  # 读：统一按可见组闭包过滤
```

**这一层只做四件事，全是横切关注点，不含任何业务逻辑**：

| 能力 | 一处实现，全局受益 |
|---|---|
| 写后 `rev + 1` | D1（`data_revision` 不再散落） |
| 写审计（谁/何时/旧值→新值） | D1（配置留痕、撤销、原创性证据） |
| 乐观锁版本校验 | N4（记录级并发） |
| 读可见性过滤 | D2（默认拒绝，漏做不可能） |

配套两条约定：
- **时间**：全项目从 `clock.now()` 取，禁止直接用 `datetime.now()` / `date.today()`（D4）
- **错误**：领域层只抛异常（统一 `SchedulerError` 子类），不再用"返回空列表"表示失败（D6）
  → 服务层按异常类型映射 HTTP 码，一处映射表

---

## 4. 成本与取舍（诚实评估）

| 反对意见 | 回应 |
|---|---|
| "又多一层抽象，MVP 要简单" | 这一层**不含业务逻辑**，只放四件横切事。不写它，这四件事要在**每个接口里重写**，净代码量更大 |
| "审计 / 乐观锁不是 MVP 必需" | **`data_revision` 已经是 MVP**（`docs/11` 定了）。写了这层，另两件几乎是白送 |
| "现在改还来得及吗" | **服务层一行代码都还没写** —— 现在定是成本最低的时刻，正是「设计阶段改设计最便宜」的体现 |

**结论：值得做。** 但范围要克制：`unit_of_work` 只实现上表四件事，
**不引入**依赖注入容器、不引入 ORM、不加领域事件总线——那些才是过度设计。

---

## 5. 顺带修一处治理缺陷：让红线可持续（D3）

把 §3 从「**现有文件只读，一行都不得改**」改为：

> **领域层改动 = 满足三条即可**，而不是一律禁止：
> 1. **31 项老测试 + `smoke.py` 全绿**（回归底线）
> 2. **新增对应断言**（改什么护什么）
> 3. **队长批准**（E2 流程）

理由：红线被反复突破后会失去约束力；改为"有条件的允许"反而更硬——
因为它把"能不能改"变成了**可验证的三条判据**，而不是一句会被绕过的口号。
