# 冗余与降级设计：做不到的时候怎么办

> 版本：v1.0（2026-10-04）｜ 归属：L12｜ 关联：`docs/17-现场演示脚本.md`、`docs/16-架构全面评估报告.md`、`docs/21-安全基线检查清单.md`
>
> ⚠️ **本文件不记「状态」**。功能是否已实现，以 WorkBuddy 项目「计划」的任务卡和仓库实际代码为准。
> 本文件回答的是另一个问题：**每件事万一做不成，会怎样。**

---

## 0. 为什么要有这份文档

一个现场演示系统，最怕的不是"功能少"，而是**在评委面前当场崩掉，而我们知道它会崩**。

这份文档把每一个可能出问题的环节的**兜底方案**提前写死，包括：

- 什么情况下要切降级
- 切到哪一层
- 用户（评委）会看到什么
- 怎么恢复

**答辩价值**：评委问「你这个东西要是断了网还能用吗」，答案不是「应该可以」，而是把这份文档翻给他看——我们有四层降级，每层的切换条件都是可判定的，不是靠现场临场决断。

---

## 1. 四层降级总览

```
        ┌─────────────────────────────────────────────┐
     L0 │ 网页界面（web/）                体验最好     │
        │ 组切换 · 周视图 · 冲突列表 · 一键消解        │
        └───────────────┬─────────────────────────────┘
                失败 ↓
        ┌─────────────────────────────────────────────┐
     L1 │ scripts/smoke.py端到端自检     自动化程度最高 │
        │ 一条命令跑完全流程，输出 PASS/FAIL 表格       │
        └───────────────┬─────────────────────────────┘
                失败 ↓
        ┌─────────────────────────────────────────────┐
     L2 │ scripts/demo_cli.py 命令行演示  🔴 保底手段  │
        │ 不过 HTTP，直接调领域层，23 处 → 0 处        │
        │ 已在main，commit d430c5a  ✅ 可用            │
        └───────────────┬─────────────────────────────┘
                失败 ↓
        ┌─────────────────────────────────────────────┐
     L3 │ 录屏 + 截图                最后一道         │
        │ 提前录好 5 分钟动线，投影播放                 │
        └─────────────────────────────────────────────┘
```

**关键设计**：L2 **不依赖 HTTP、不依赖浏览器、不依赖前端**。这是它能当保底的原因——现场演示可能挂的东西很多，但 Python 进程本身很难挂。

## 2. L0 → L1：网页不可用时的降级

### 2.1 触发条件

| 现象 | 判断方法 | 是否降级 |
|---|---|---|
| 页面 404 | 访问 `/` 返回 `{"error": "静态资源目录不存在…"}` | ✅ 切 L1 |
| 页面空白、控制台报 JS 错 | 浏览器 F12 | ✅ 切 L1 |
| `/api/conflicts` 返回 404 | curl 看状态码 | ✅ 切 L1 或 L2 |
| `/api/conflicts` 返回 500 | curl 看响应体 | ✅ 切 L2（L1 也依赖接口） |
| 页面显示「无冲突」但明明该有 | 见 §5 静默跳过 | ❌ **不降级，这是 bug** |

🔴 **最后一行很重要**：「显示无冲突」和「真的没冲突」在界面上长得一模一样，**降级解决不了这个问题**，必须修代码。降级只处理"跑不起来"，不处理"跑错了"。

### 2.2 降级动作

```bash
# 1. 先确认是前端问题还是后端问题
curl http://127.0.0.1:8000/api/health          # 后端活着吗
curl -I http://127.0.0.1:8000/                   # 前端资源在吗

# 2. 后端活着但前端404 → 重建演示库 + 确认分支
python scripts/reset_demo.py
git branch --show-current                        # 必须是 main

# 3. 跑端到端自检，看问题出在哪一环
python scripts/smoke.py
```

### 2.3 用户可见文案

L1 模式下不要投屏 `smoke.py` 的原始输出（评委看不懂 PASS/FAIL 表）。正确做法是**一边跑一边解说**：

> 「这是我们的自动化端到端自检，30 秒内会跑完整个流程——建库、起服务、四个接口各调一次、消解一次、复扫一次。每一步都有明确的判据，比如消解后剩余冲突必须是 0，否则脚本会以非零退出码失败。」

### 2.4 恢复路径

L1 跑通说明领域层和接口层都正常，问题在静态资源或前端。此时回L0 修前端，不影响已验证的后端。

## 3. L1 → L2：接口层挂了时的降级（🔴 现场最常走的一条）

### 3.1 为什么 L2 能救

`demo_cli.py` **完全绕过 HTTP 和前端**，直接调领域层：

```
浏览器 → http.server → routes.py → api_*.py → scheduler/领域层
                ↓ 挂了
   python demo_cli.py ─────────────→ scheduler/领域层
```

只要Python 和 SQLite 能跑，L2 就能完整演「冲突检测 → 一键消解」。

### 3.2 触发条件

- `/api/resolve` 500（消解接口异常）
- `/api/objects`、`/api/schedules`、`/api/conflicts` 任一 500
- 端口被占用且换端口也失败
- 前端一直404 且时间不够修

### 3.3 降级动作

```bash
python scripts/demo_cli.py
```

**预期输出（已实测，逐字一致）**：

```
冲突：23 处
→ 应用方案第 1 处…
冲突：12 处
→ 应用方案第 1 处…
…
冲突：0 处
✅ 全部消解完成
```

### 3.4 用户可见文案

> 「这是我们的命令行版本，走的是同一套求解器，只是绕开了网页层。大家看这里的数字——23 处冲突，消解后 0 处，全部是当场跑出来的，不是录好的。」

🔴 **台词不要改**。L0 和 L2 用的是同一套口径（`raw_count = 23 = scan().count`，与 L0 的 `remaining_before` 同源），所以解说词可以完全通用。

### 3.5 恢复路径

L2 成功说明领域层完好，问题在服务层。赛后修服务层，不影响领域层正确性。

---

## 4. L2 → L3：连Python 都不利索

### 4.1 触发条件

- Python 环境损坏（现场换机、换账号）
- 依赖缺失（本项目零第三方依赖，这种情况极少见）
- 磁盘/权限问题导致 SQLite 无法写入

### 4.2 降级动作

播放提前录好的 5 分钟录屏。录屏**必须**满足：

- 从 `reset_demo.py` 开始录，**包括重置库的过程**（体现"可复现"）
- 终端字号调大到评委能看清
- 鼠标点击放慢，必要时加字幕或旁白
- 时长控制在 4 分 30 秒内，留问答时间

### 4.3 用户可见文案

> 「我先放一段完整的实录，这是上周彩排的版本。除了时间戳，屏幕上的每一个数字都是当场跑出来的。」

**为什么要说"上周彩排"**：录屏在诚实范围内是正常工程手段（预录备份），但**不能谎称是现场实时运行**。评委问起时坦白说明，反而是加分项——说明我们有Plan B。

### 4.4 恢复路径

纯演示手段，无需恢复。

## 5. 静默跳过：不是降级能解决的问题（🔴 单独一节）

前面四层处理的是"**跑不起来**"。这一节处理"**跑起来了但结果不对**"——**比跑不起来更危险**，因为它不报错。

### 5.1 已知的七处同源问题

领域层有五处「静默跳过」，共同后果是**假阴性**（本该报冲突却报"无冲突"）：

| # | 位置 | 触发场景 | 后果 |
|---|---|---|---|
| 1 | 午休活动 | 午休时段 `mask = 0` | 该活动被当作"不占用"而跳过 |
| 2 | 学期外 | 日期不在任何学期内 | 该天的日程不参与冲突检测 |
| 3 | 调休 `makeup` | `kind='makeup'` 未实现分支 | 调休上课日不参与检测 |
| 4 | `v_schedule_full` 视图 | 视图用 `JOIN`（INNER） | 孤儿日程行被静默丢弃 |
| 5 | `aligned` 字段 | 时间未对齐到节次边界 | 该条占用被丢弃 |

🔴 这五处的**共同特征是"不报错"**。系统返回 200，界面显示"无冲突"，一切看起来正常。

**2026-10-04 又查出两处，同属"绿灯不等于正确"，详见 §5.2.2 / §5.2.3**：

| # | 位置 | 触发场景 | 后果 |
|---|---|---|---|
| 6 | `api_health.py` 的 `ok` 字段 | 契约测试就绪判定字段名不符 | 17 项契约测试 `Ran 0 tests` + `OK`，**从未真正执行** |
| 7 | `api_*.py` 命名约定 | 纯业务内核模块用了 `api_` 前缀 | 服务启动即 `RuntimeError`，且报错指不到真因 |

🔴 **第6 处是本项目至今最隐蔽的一处**：单测全绿、doctor 14/14、全量 110 项全绿，
而契约级合规性一条都没验过。**七处的共同教训是同一句话——
「绿灯不等于正确，合并/新增类风险必须真实打一次请求或跑一次命令」。**

### 5.2 统一修法

用 **`UnmappedTime` 信号 + `skipped` 计数**：

- 任何"无法映射到槽位"的时间片，产出一个 `UnmappedTime` 记录，**不静默丢弃**
- 响应体带 `skipped` 计数
- 前端在 `skipped > 0` 时显示提示：「有 N 条日程时间未对齐到节次，未参与冲突检测」

### 5.2.1 🔴 已实测确认的静默失效：节假日整周返回 0 冲突

**2026-10-04 实测**（真实 HTTP，非推理）：

```bash
# 把演示日期设到国庆假期（10/1–10/7 无课，calendar_exceptions有 holiday 行）
python scripts/run_server.py --today 2026-10-01
curl "http://127.0.0.1:PORT/api/conflicts"
# → {"count": 0, "raw_count": 0, "items": [], "window": {"from":"2026-09-28",...}}
```

**现象**：接口返 **200 +0 冲突**，没有任何错误提示。
但库里**确实有 1280 条日程**，只是那一周全被 `holiday` 排除了。

**代码位置**：`occupancy.py:127` — `exceptions.get(d.isoformat()) != "holiday"`
为假时该天被跳过，**但不计入任何计数**。

**🔴 为什么它比崩溃危险**：
- 崩溃 → 用户知道出事了，会重试
- **静默返 0 → 用户以为"我的课表没冲突"，这比报错有欺骗性得多**
- 若现场演示前误设日期，页面会显示「无冲突」并配一句「太棒了，没有冲突要处理」——
  **评委会认为我们的系统检测不出冲突**

**修法**（与 §5.2 同一套`UnmappedTime` 机制）：

```python
# 伪代码
if exception_kind == "holiday":
    skipped.append(UnmappedTime(date=d, reason="holiday",
                                note="节假日，课程按校历不上课"))
    continue#🔴 但必须记录，而不是静默丢弃
```

响应体加 `skipped` 与 `scanned_days` 两个字段：

```json
{
  "count": 0, "raw_count": 0, "items": [],
  "window": {"from": "...", "to": "...", "today": "..."},
  "scanned_days": 0,
  "skipped": 3,
  "skipped_detail": [
    {"date": "2026-10-01", "reason": "holiday", "note": "国庆假期"},
    ...
  ]
}
```

**前端显示**：当 `scanned_days == 0 && count == 0` 时，
显示「本窗口没有任何可扫描的上课日（可能整周为假期）」，
🔴 **绝不显示「无冲突」**。

**幂等判据**：`scanned_days == 0` 时接口仍返 200，但**必须**带 `skipped > 0`；
两者都满足才算修好（否则会误报"今天真的没课"这种合法情况）。

**这正是 §5.2 说的"五处静默跳过"里影响最大的一处** —— 其余四处影响单个日程，
这一处影响**整整一周**，且最容易在演示前被误触发。

### 5.2.2 🔴🔴 契约测试 `test_contract.py` 一直在skip（2026-10-04 实测发现）

**这是本次最隐蔽的一处：一份 40+ 项的契约测试，从上线起就没真正跑过。**

`tests/test_contract.py` 的 `setUpModule()` 逻辑：

```python
if not (st == 200 and body.get("ok") is True):
    raise unittest.SkipTest(f"服务未就绪：GET /api/health 返回 {st} {body!r}，期望 200 {{\"ok\": true}}")
```

**实测对照**：

| | 内容 |
|---|---|
| 契约 `docs/07 §9` 冻结 | `{"ok":true}` —— 🟡 **只返回这一句**，不带版本号/路径（**公网下避免指纹识别**） |
| B1 实现 `api_health.py` 实测 | `{"status":"ok","server_date":"2026-09-08","asset_version":"20261003","db":"ok"}` |
| 结果 | 字段名不符 → `SkipTest` → **40+ 项契约测试整体跳过，`Ran 0 tests`，退出码仍是 OK** |

**🔴 为什么它比崩溃危险**：
- 单测全绿、doctor 14/14 全绿、110 项discover 全绿
- 但**契约级合规性一条都没验**（聚合是否做了、a/b 字段是否给全、前端结构是否对）
- 而 `discover` 的 `skipped=1` 混在 110 项里，**极易被当成"只是环境没起服务"**而忽略

**修法（两处，只能二选一，建议 A）**：

| 方案 | 动作 | 权衡 |
|---|---|---|
| **A. 改实现对齐契约**（推荐） | `api_health.py` 只返 `{"ok":true}`，把版本/日期/db 挪到 `/api/version` | 🔴 契约 §9 写明「**避免指纹识别**」，这是**安全考量**，不该为测试便利破坏它 |
| B. 改测试放宽 | 契约测试接受 `status=="ok"` | ❌ 等于用测试迁就实现，丢掉契约的安全意图 |

⚠️ 现状是**实现违背了契约的安全意图**（多返了 asset_version 等指纹信息），
而测试没抓到。**这是"契约测试没跑"的直接后果。**

**排查建议（沉淀为方法）**：
🔴 任何 `unittest` 出现 `Ran 0 tests` + `OK` 的组合，**一律当作失败处理**，
不能因为退出码是 0 就放过。已列入 `docs/21 §5 静默失效专项`。

**✅ 实际修法（2026-10-04 落地，与上文建议不同——此处为实测后的真实结论）**：

最终采用了**上面的方案 A 的一半 + 一个折中**，理由是执行时才发现上文漏了一个约束：

```python
# api_health.py
payload = {
    "ok": True,                    # ← 契约 §9 冻结的唯一必返字段，补上
    "status": "ok" if db_state == "ok" else "degraded",
    "server_date": cfg.today.isoformat(),
    "asset_version": cfg.asset_version,
    "db": db_state,
}
if db_state != "ok":
    payload["ok"] = False
    return 503, payload
```

**为什么不是纯方案 A**：上文说「把版本/日期/db 挪到 `/api/version`」，
但 `scripts/doctor.py` 的 14 项自检里有**三项**依赖 `server_date` 和 `db`
（「/api/health 返回 200」「健康检查反映注入日期」「任意日期注入生效」）。
doctor 是 B1 的红线验收项，拆接口会连带改 doctor。

| 项 | 状态 |
|---|---|
| 契约测试 |✅ 17项首次真正执行（此前 0 项） |
| doctor | ✅ 14/14 仍全绿（`server_date`/`db` 保留即可） |
| 契约 §9 安全意图 | ⚠️ **未完全满足**——仍多返了指纹类字段 |
| 收口动作 | 🔴 **CP-H 上公网前必须收紧到只返 `ok`**，届时同步改 doctor |

**🔴 顺带查出第二处测试自身缺陷（同一天）**：
`test_default_week_starts_monday_and_is_this_week` 用 `date.today()`（机器日期）
断言「week 缺省 = 本周」，但服务支持 `--today` / `SCHEDULER_TODAY` 注入演示日期
（现场演示要能复现同一结果，这是 B1 红线）。服务 `--today 2026-09-08` 时该项报
`2026-09-07 != 2026-09-28` —— **看起来像实现 bug，实际是测试取错了日期来源**。

修法：`setUpModule` 缓存 `/api/health` 的 `server_date`，新增 `server_today()`
供所有「本周 / 缺省」类断言使用。这正是上面 `server_date` 暂时保留的**第二个理由**。

### 5.2.3 🔴 内核模块不能叫 `api_*.py`（2026-10-04 实测发现）

**症状**：B3 三个接口写完后，服务**根本起不来**：

```
RuntimeError: server.api_kernels 未导出非空 ROUTES
```

**根因**：`src/server/routes.py` 用约定式路由 —— `os.listdir` 扫 `src/server/api_*.py`，
逐个读模块级 `ROUTES`，要求它**必须是非空 dict**（**空 dict 也抛**）。三道门槛：

| 门槛 | 要求 |
|---|---|
| 文件名 | 必须以 `api_` 开头（否则扫不到，路由不注册 → 404） |
| `ROUTES` | 必须存在且为**非空** dict（空 dict 抛 `RuntimeError`） |
| 路径 | 必须以 `/api/` 开头 |

问题在于：为了让 B3 三个接口**共用同一套口径**（避免同一口径在多个接口各算一遍
而漂移——B4 的 `_slots_hex` 写过两遍就是这个教训），抽了一个纯业务内核模块
`api_kernels.py`。**它一个路由都不注册**，却被扫到并要求导出非空 `ROUTES`。

🔴 **这类失败发生在服务启动时，且报错信息完全指不到真因**（"未导出 ROUTES"
看起来像忘了写路由，实际是文件名不该用 `api_` 前缀）。属于典型的静默失效——
因为它至少会报错，**真正危险的是它哪天没报错**。

**修法（守住「不改 `routes.py`」红线）**：改名 `api_kernels.py` → **`b3_kernels.py`**，
跳出 `api_*.py` 的 glob 范围。`routes.py` 一行不用改，`scan()` 从 7 条恢复到 8 条。

**沉淀为命名铁律**：
> **`src/server/api_*.py` = 接口层（必须导出非空 `ROUTES`）；**
> **业务内核、工具、适配层一律不得用 `api_` 前缀。**
> 加新文件时先问自己：它注册路由吗？不注册就别叫 `api_*`。

**排查方法**（比读代码可靠）：
```bash
python scripts/doctor.py    # 「约定式自动注册发现路由」一项会直接报出扫到了几个
```
doctor 的这一项就是为此设的——**它会打印出实际扫到的模块名与路由数**，
比人肉翻目录可靠。已列入 `docs/21 §5 静默失效专项`。

### 5.3 用户可见文案

> 「本次扫描有 2 条日程的时间没对齐到整节（比如 14:15–15:00），没有参与冲突检测。系统会明确提示这一点，而不是假装扫过了。」

**这一段话在答辩时是加分项**：它证明我们**知道自己系统的边界在哪**，而不是以为自己什么都对。

### 5.4 恢复路径

不适用——这是必须修的 bug，不是可以降级的场景。

## 6. 其他降级场景

### 6.1 求解超时 / 限流

**事实**：`/api/resolve` 有 `RATE_LIMIT = 10`（每 token 每分钟 10 次），超限返回 **429**。

| 触发条件 | 降级动作 | 用户可见文案 |
|---|---|---|
| 第 11 次请求 | 返回 429 | 「操作太频繁，请稍等几秒」|
| 求解超时 | 见§6.2 | 「本次求解超出时间预算，已给出部分方案」|

🔴 **答辩要点**：限频不是"限制用户"，是**防现场被反复点击点爆**。而且它有明确的判据（第 11 次必429），可现场验证。

### 6.2 求解性能

**实测**：扫描一周 1280 条日程约 1.50 秒 / 约 239MB 内存。一键消解约 50 次全量重建 ≈ 75 秒，在 1GB 轻量云服务器上有 OOM 风险。

**缓解措施（已实施）**：限制扫描窗口 ≤ 2 周。

**未实施的架构级优化**：「读时上卷」（read-time rollup，把 125 万次查询降到约 2.6 万次，降48 倍）。**说清楚它没做，比假装做了好。**

### 6.3 断网

**这是本项目的强项，不是降级场景**：

- 技术栈是 **Python 标准库 + SQLite**，零第三方依赖
- 前端原生 JS，无构建步骤、无外链 CDN
- 🔴 所有功能在完全断网的机器上都能跑

**现场要做的**：

```bash
# 拔网线（或 Windows 防火墙断网），然后
python scripts/reset_demo.py
python scripts/run_server.py --today 2026-09-08
python scripts/demo_cli.py
```

全部应正常。**建议在彩排时真的拔一次网线**——口头说"断网也能跑"和现场拔网线是两种可信度。

### 6.4 端口占用

| 现象 | 处置 |
|---|---|
| 起服务报端口占用 | `python scripts/run_server.py --port 8123` |
| 改端口后前端取不到数据 | 前端用**相对路径** `api/xxx`，自动跟随端口 |
| 仍不行 | 切 L2（`demo_cli.py` 不占端口） |

### 6.5 数据库损坏

| 触发条件 | 降级动作 |
|---|---|
| SQLite 报 `database is locked` | 关掉其他占库的进程；`run_server.py` 每请求新建连接，不会长期持锁 |
| 数据库文件损坏 | `python scripts/reset_demo.py` 重建（演示库可随时重建，这是它叫"演示库"的原因） |

**代价**：重建会丢失运行时数据。但演示场景下数据可重建，所以这不是真损失。

## 8. 彩排建议（10/6 或 10/7 做一次）

⏱ 约 30 分钟，**建议在真机、投影、断网条件下各做一次**。

| 序号 | 演练项 | 通过判据 |
|---|---|---|
| 1 | L0 正常流程 | 5 分钟内走完组切换 → 周视图 → 冲突列表 → 一键消解 |
| 2 | 🔴 带 `--today` 启动 | `remaining_before = 23`（不带只扫到 1 处，**且不报错**） |
| 3 | 拔网线重跑 | `demo_cli.py` 仍23 → 0 |
| 4 | 手动杀掉服务 → 切 L2 | 台词不变，23 → 0 |
| 5 | 制造端口占用 | 换端口后能起 |
| 6 | 故意注释掉一个路由 | `doctor.py` 报 FAIL（证明自检真的能抓问题） |
| 7 | 完整走 2 遍 | 第二遍计时，确认 ≤ 5 分钟 |

🔴 第 2 项是最容易翻车的一项，详见 `docs/17 §1`——不带 `--today` 时系统**不报错**，`termination` 仍是 `ok`，页面显示"已消解 1 处冲突"，比直接报错更难解释。

## 9. 答辩口径

如果被问「你这个系统靠不靠谱」，可以这样答：

> 我们把「靠不靠谱」拆成了可判定的四层。网页层跑不通，有端到端自检脚本；自检跑不通，有不依赖网页的命令行版本，它绕过 HTTP 直接调求解器，23 处冲突当场消到 0；连这个都不行，还有提前录制的实录。每一层的切换条件都是能当场判断的，不是靠临场决断。
>
> 但比降级更重要的是我们知道边界在哪。我们的系统有五处"静默跳过"会导致漏报，我们不打算藏这一点——界面会明确告诉你有多少条日程没参与检测。做排课系统的，假装自己什么都对，比承认边界在哪更不可信。
