# 课表活动撞车难调，AI求解一键消解

> 仓库名：`scheduler`（刻意不叫 school-scheduler：模型不绑定学校场景，
> 组织树、节次、资源全部可配置，后续可推广到培训机构排课、企业培训与会议室排期）

中学的课表（长期重复事务）和活动（一次性事务）通常各管各的：排课时看不见已安排的活动，
于是撞车；出了冲突又只能靠人反复试。本项目把两者归一化到同一套底层模型——
「某个对象在某天的哪些节次被占用」——用位运算做统一的冲突检测，再让自建的约束求解器
做自动排布与一键消解：硬约束（教师、教室、班级撞课）保证百分之百满足；
软约束（连堂、单日课时上限、主科不排末节等）以代价形式参与权衡。

权限上，「可被调度的对象」与「可登录的账号」是正交的两层：谁能在哪个组里看什么、改什么，
由沿组织树继承的四档授权决定；学生一定在对象图里，但不一定需要账号。
永久性的改动走审批流：提议 → 上级批准 → 才真正落库。

**全部计算在本地完成，断网也能运行。**

## 五条最重要的设计约定

1. **对象 ≠ 账号。** `objects` 里可以有 1500 个学生行（用于调度与冲突检测），
   `users` 里只放真正需要登录的人。学生不持有终端，就不必发密码。
2. **位图是加速层，不是真相层。** 真相是 `period_slots` 配置 + 周期规则 + 起止时刻；
   位图只在检测时展开出来，让冲突判断变成一次按位与。
3. **课表与活动共享底层。** 两者都归一化为「(日期, 当天槽位掩码)」，
   冲突检测只有一套位运算。这样排课才看得见已安排的活动，不会撞车。
4. **权限按组、四档、沿组织树继承。** 查看 → **提请求** → **批下级的请求** → **改组结构并批永久改动**；
   多条路径取最高档；全局角色是天花板；**刻意不做负权限**（多父结构下语义不自洽）。
   🔴 安全实现与审查**必须分离**：实现归后端，审查归队长，不得同一人。
5. **AI 只负责"听懂"和"解释"，不负责"算"。** 求解分三步（理解需求 / 搜索计算 / 解释与微调），
   **只有第 ② 步严禁交给大模型**。大模型可提调整建议，但每一条都必须回送硬约束校验，不通过即驳回。
   **本地规则解析器是主力**，云端模型仅作可选增强，失败自动回落，断网不受影响。

更多说明见 [`docs/00-架构速览.md`](docs/00-架构速览.md)。

## 已知限制（诚实列出）

- 暂不支持调课补课 `makeup`（数据模型已定义，功能未实现，已列入 B0）。
- 跨天活动需拆成两条一次性日程，且必须属于同一组。
- 非整节（如 14:15–15:00）的安排按连续区间处理，不做精确切分。
- 偏好权重学习、拖拽排课、全局排课均**未实现**（见上文「暂缓」）。
- 三个 P0 静默缺陷中，**P0-1（`rebuild_closure` 清空闭包表）已修复并合入 `main`**，回归测试见 `tests/test_p0_1.py`。

- **P0-2（调休 `makeup`）、P0-3（5 处同源「静默跳过」）仍未修**，见 `docs/16` 与 `docs/21 §5`。

## 数据与安全红线

- 数据库文件（`data/*.db`）**不入库**：里面会有真实学生名单与课表，按学校规定不得外传。
- 对外演示、试用、上线**一律使用脱敏的「试用组织」数据**。
- 演示与现场必须**断网也能跑**，不依赖任何外部 API。
- 发给外部大模型的内容**只能是用户指令文本**，严禁携带课表、班级名、姓名、联系方式。
- 禁止编造校方规章、作息、人数细节；不确定的一律列为待确认。
